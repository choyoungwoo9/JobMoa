# 직무별 수집 지원과 판별 기준

이 문서는 현재 제품의 수집 지원 범위와 판별 동작을 설명한다. [일반 분류 규칙](classification-rules.md)을 제품에 적용했으며 [고정 정답 평가](analysis/classification-evaluation-v0.5.md)는 개발 스냅샷의 평가다.

직무를 먼저 선택하면 해당 분야의 수집을 지원하는 회사가 기업군 아래 표시됩니다. 지원 여부는 회사별 판별 규칙이 구현돼 있다는 뜻이며, 현재 해당 직무의 공고가 존재하거나 모든 회사의 실사이트 수집 검증을 마쳤다는 뜻은 아닙니다.

## 자동 분류 분야

저장되는 모든 공고에 [일반 판정 규칙](classification-rules.md)을 적용한다. 제목보다 담당 업무를 우선하며, 협업 상대·자기 업무의 도구 사용·우대 경험만으로 태그를 추가하지 않는다. 일반 Software Engineer도 명확한 업무 근거가 있으면 분류한다. 여러 규칙을 통과하면 복수 직군을 연결하고, 웹 양쪽을 실제 담당하는 풀스택은 백엔드·프론트엔드에도 연결한다. 양자택일 배치는 해당 분야에서 조회하되 풀스택으로 간주하지 않는다. 제외 조건과 직군별 상세 포함 기준은 일반 규칙 문서가 기준이다.

- 서비스·시스템: 웹 백엔드, 프론트엔드, Android, iOS, 풀스택, 임베디드·시스템 SW, 로보틱스·자율주행, QA·테스트 자동화.
- 데이터·AI·인프라: 데이터 엔지니어, ML 엔지니어, AI 응용·에이전트 개발, ML 플랫폼/MLOps, DevOps/SRE, 클라우드·시스템 인프라, DBA/데이터베이스, 데이터 분석·BI.
- 기획·비즈니스: 기획·전략, PM, 디자인, 마케팅, 영업·사업개발.

`all`은 수집 범위이며 태그로 저장하지 않는다. 미분류는 직군이 없는 상태로, 별도 조회 탭에서 확인한다. 새 8직군(`ai-application`, `ml-platform`, `cloud-infrastructure`, `database`, `embedded-system`, `robotics`, `qa-test`, `data-analysis-bi`)은 자동 분류·조회용이며 분야별 수집 회사는 아직 등록하지 않았다. 전체 수집의 어댑터가 먼저 제외한 공고를 분류기가 복원하는 구조는 아니다.

## 회사별 규칙과 중복 처리

`CategoryClassifier`는 `(companyId, categoryId)`로 규칙을 조회합니다. 기존 사이트에는 사이트별 직함 사전이 있고, 새 9개 사이트는 회사별 공통 개발 직함 사전을 사용하며 어댑터의 공식 직군 후보 필터를 먼저 적용합니다. 계열사의 직함 및 일본어 표현이 다른 경우 별도 규칙을 둡니다. 예를 들어 토스의 `Server Developer`, LINE의 `Server Engineer`, LY 일본의 `サーバーサイド`는 각각 해당 회사 프로필에서 해석합니다.

새로 추가한 9개 사이트의 전산 지원은 [회사별 수집 문서](README.md#수집기와-지원-범위)의 상세 기준을 참고하세요. 구현된 조합은 실제 수집 버튼을 누른 검증과 다릅니다. 여기어때는 현재 공식 Greeting 채용 포털의 기술 직군 목록과 Android Developer 상세 1건을 브라우저에서 확인했으며 전체 수집 파이프라인 검증은 아직 하지 않았습니다. 이전 403은 공식 채용 페이지가 아닌 `internship.yeogi.com` 주소에서 발생했습니다.

각 사이트 어댑터의 공식 직무·조직 분류 → 회사별 목록 제목 후보 → 일반 규칙의 최종 본문 판정 → 저장 순서다. 회사별 후보 탐색의 보수적 범위는 유지하므로, 세부 분야 수집이 전체 수집 후 분류한 모든 공고를 발견한다고 보장하지 않는다. 저장 시에는 선택한 분야와 무관하게 21개 규칙을 적용한다. 재수집·저장 본문 재분류 시 자동 태그를 교체하며 본문 내용이 같으면 캡처·본문 버전은 재사용한다.

## 검증 범위

2026-11-14 통합 검증에서 외부 요청 없이 로컬 표본 294개 assertion을 통과했습니다. 개발 8개·비개발 5개 분야의 직함과 본문 근거, 풀스택 양쪽 업무, 모호한 Software Engineer·분석/연구 직무 제외, PM/PO·세일즈·Design Lead, Marketing Designer의 디자인/마케팅 구분, 카카오 계열사 AI 직함의 구현 근거, 회사별 지원 조합을 확인했습니다. 오늘의집 공식 목록 캐시로 후보 30개, URL 중복 제거·정규화·허용 호스트와 경로도 별도 검증했습니다. 실제 버튼 수집 결과는 아래와 같습니다. 이는 모든 회사·분야 조합의 실사이트 수집 성공을 보장하는 전수 검증이 아닙니다.

카카오페이증권의 재오픈 공고에 과거 `closedAt`이 남아 마감으로 숨겨지는 문제를 발견해 현재 종료 상태·명시적인 마감일 기준으로 수정했다. 해당 공고만 한 번 재수집해 진행 중으로 복원했다. 수정 과정에서 마감 상태 자체를 내용 해시에 넣던 기존 동작도 발견했으며, 최종 구현은 상태만 바뀌면 새 캡처·본문 버전을 만들지 않는다. 상태 변경과 과거 해시 호환은 외부 요청 없는 실제 JPA 트랜잭션 표본으로 확인하고 롤백했다. 수정 이전에 생성한 버전·수집 기록은 보존했다.

서버 적용은 사용자가 진행 중이던 전체 수집이 끝난 뒤 수행했으며 기존 302개 공고를 보존했다. 이 작업에서는 위 표본만 수집했고, 전체 기업·분야 조합을 반복 수집하지 않았다. 카카오페이증권 문제 분석을 위한 상세 1회 조회 외에 오류 없는 공고를 별도로 반복 탐색하지 않았다.

화면에서는 14개 분야 탭·API 분야 설명·비개발 지원 회사 한정·분야와 계열사가 표시되는 기록·저장 본문/캡처·자동 읽음을 확인했다. 1440px와 390px에서 페이지 가로 넘침 없이 분야를 스크롤하고, 모바일 수집 창의 고정 하단 버튼이 화면 안에 유지되는 것을 확인했다. 샘플 모드의 오늘의집 디자인 수집 미리보기도 완료했으며 실제 수집 API는 호출하지 않는다.

기획·디자인·마케팅·영업 및 나머지 개발 분야는 로컬 판별·캐시 검증을 포함한 구현 범위다. 이번 버튼 검증에 포함하지 않은 실제 상세 공고까지 모두 검증했다고 간주하지 않는다. 정식 테스트 소스 파일은 추가하지 않았다.


### 비개발 사이트 확장 검증 · 2026-11-15

기획·PM·디자인·마케팅·영업을 토스 9개 계열사와 당근·당근페이로 확장했다. 오늘의집을 포함해 비개발 분야당 3개 사이트·12개 회사가 지원 대상이다. 개발 8개 분야는 유지하고, 당근의 `Software Engineer, Data`·`Software Engineer, Machine Learning` 직함과 본문 근거도 로컬 표본으로 확인했다. 전체 판별 표본은 304개 assertion을 통과했다. 회사별 후보 조건과 실제 버튼 결과는 [비개발 사이트 문서](non-development-sources.md)를 따른다.
