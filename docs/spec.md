# JobMoa 제품 스펙

## 사용 환경과 현재 범위

- 개인 전용 로컬 도구다. Kotlin · Spring Boot · Spring Data JPA · MySQL, React 화면을 Docker Compose로 실행한다.
- 기본 화면은 실제 API·DB·Playwright 수집기를 사용한다. `?demo=1`은 별도 localStorage 기반 화면 검토용 샘플이며 실제 수집이나 PNG 캡처가 아니다.
- 기존 공고·읽음·버전·수집 기록은 재시작과 기능 추가 시 유지한다. 데이터 초기화는 사용자가 명시한 경우에만 별도로 수행하며 자동 마이그레이션에서 삭제하지 않는다.

## 수집 사이트·회사·분야

- 네이버·토스·카카오·쿠팡·당근·LINE·우아한형제들·오늘의집과 쏘카·컬리·무신사·야놀자·리디·채널코퍼레이션·여기어때·뱅크샐러드·직방의 공식 개발 직무 범위를 지원한다. 새 9개 사이트는 기획·PM·디자인·마케팅·영업을 아직 수집하지 않는다.
- 수집 사이트와 회사는 별개다. 하나의 통합 포털에 여러 계열사가 게시할 수 있으며, 회사 카탈로그에서 포털과 지원 분야를 연결한다.
- 수집은 분야 선택 → 해당 분야를 지원하는 기업군·계열사 선택의 두 단계다. 기업군 체크로 지원 계열사를 일괄 선택하고 계열사를 개별 해제할 수 있다.
- 지원 여부는 회사 × 분야 조합의 수집 규칙이 구현됐는지를 뜻한다. 지원하지만 공고가 0건인 경우는 정상 수집이다.
- 목록 메타데이터로 후보를 좁히고 본문 업무 근거로 최종 판별한다. 본문에 직무 단어가 있다는 이유만으로 포함하지 않는다. 분야별 수집은 근거가 부족하면 제외한다. 전체 수집으로 저장된 공고의 직군 근거가 부족하면 미분류 탭에서 확인한다.
- 구현된 지원 범위와 실제 사이트에서 검증한 표본 범위는 구분한다. 사이트·공고 구조 변경과 접근 제한은 실패 기록에 남긴다.

## 지원 직무와 경계

- 개발: 웹 백엔드, 프론트엔드, Android, iOS, 풀스택, 데이터 엔지니어, ML 엔지니어, DevOps/SRE.
- 비개발의 첫 범위: 기획, PM, 디자인, 마케팅, 영업. 비개발은 오늘의집·토스 계열사·당근·당근페이에서 지원한다. 다른 포털은 기존 개발 범위를 유지하며, 사이트마다 공식 직군과 직함 규칙을 따로 적용한다.
- `all`은 선택한 회사에서 구현된 수집 범위의 전체 공고다. 각 회사의 구현된 지원 범위를 따르며 토스·당근 국내·오늘의집은 지원하는 개발·비개발 분야를 포함한다.
- 풀스택은 웹 UI와 서버 개발 양쪽의 담당 근거가 필요하며, 판정되면 웹 백엔드·프론트엔드에도 연결한다.
- 데이터 엔지니어와 데이터 분석가·사이언티스트를 구분한다. ML 엔지니어는 모델 구현·학습·추론 서비스 업무를 확인하며 순수 연구 직무는 제외한다.
- 일반 Software Engineer, 막연한 운영·매니저처럼 분야를 특정하지 못하는 직함은 제목만으로 임의 배치하지 않는다. 담당 업무가 명확하면 해당 규칙으로 분류한다.
- 분야별 구체적인 포함·제외 기준과 회사별 지원 범위는 [직무 분류 기준](job-categories.md)에 기록한다.

## 공통 큐와 저장

- 실행에는 선택한 분야·계열사를 저장한다. 포털별 목록 탐색은 독립 작업이고 공고는 공통 MySQL 큐에서 빈 작업자가 가져간다.
- 기업별 전담 작업자를 두지 않는다. 작업자 수와 사이트별 동시 활성 페이지 수를 별도 설정한다. 기본 작업자 3개·사이트별 1개이며 전체 반복 수집을 최소화한다.
- 작업자는 자신의 스레드에서만 Playwright와 브라우저를 생성·재사용·종료한다. 쿠팡 상세는 일반 브라우저 모드와 Docker 내부 Xvfb 화면을 사용한다.
- DB에는 대기·처리 중·완료·실패와 단계별 체크포인트·임대 토큰을 저장한다. 재시작 시 임대 만료 작업을 복구한다. 브라우저 탐색·캡처는 DB 트랜잭션 밖에서 수행한다.
- 동일 URL로 식별되는 공고는 공유하고 여러 분야 카테고리를 연결할 수 있다. `all`은 별도 공고 태그가 아니다. 읽음·최초 발견일·버전도 공고 단위로 공유한다.
- 선택한 수집 분야와 무관하게 저장 시 전체 직군 규칙을 적용해 모든 통과 분야를 연결한다. 재분류 시 이전 자동 태그를 새 판정 집합으로 교체한다.
- 본문 해시를 캡처 전에 비교한다. 동일하면 기존 버전·캡처를 재사용하여 본문과 캡처를 다시 저장하지 않는다. 변경 시에만 새 버전을 보관하고 최초 발견일을 유지한다. 마감 상태만 변경된 경우 본문·캡처 버전을 추가하지 않고 상태만 갱신한다.
- 완료 작업의 임시 본문은 제거하고 본문 원본은 버전에 보관한다.
- 마감 공고는 보존하되 기본 목록에서 숨긴다. 목록 누락·일시적인 조회 실패만으로 마감을 확정하지 않는다.

## 공고 탐색과 개인 관리

- 공고 모아보기 첫 화면은 공고 표를 주 콘텐츠로 바로 보여준다. 장식용 소개·통계 카드는 표시하지 않는다. 완료된 최근 수집은 시각과 신규·관심 변경·마감·실패 건수를 한 줄에 모으며, 각 건수를 누르면 해당 결과를 공고 목록에서 확인할 수 있다. 수집 기록 링크는 기업별 상세로 이동한다.
- 직군 선택은 그룹과 건수를 함께 보여주는 검색 팝오버로 제공한다. 선택한 직군은 버튼에 표시하고, ‘전체 직군’ 항목으로 초기화한다. 직군 건수는 현재 회사·기업군·마감 포함 범위로 계산한다. 좁은 화면에서는 팝오버를 화면 안의 바텀 패널로 배치한다.
- 전체 조회와 분야별 조회를 제공한다. 회사·공고명·근무지를 검색하고 최초 발견일 최신순·오래된순 또는 회사 이름순으로 정렬한다. 페이지 크기는 8·20·50개에서 선택하고 기본은 20개다.
- 기본 목록은 표형으로 회사·공고명·직군 태그·근무지·최초 발견일·원문 링크·읽음을 보여준다. 경력·마감일은 모든 사이트의 공통 필수 추출값이 아니다.
- 공고명 또는 ‘상세 보기’를 누르면 현재 표 오른쪽에 상세 패널이 겹쳐 열린다. 배경 표는 너비·검색·정렬·페이지·스크롤을 유지한다. 상세를 닫으면 원래 목록으로 돌아오며, 이전·다음은 열었을 때의 필터 결과 순서를 따른다.
- 공고 열람 시 자동으로 읽음 처리한다. 상세는 저장된 캡처를 먼저 표시하고 저장 본문·변경점·이전 버전을 전환할 수 있다. 캡처는 상세를 열 때 불러오며 확대할 수 있다. 마감 공고에는 보관 상태와 마지막 마감 확인 관측 시각을 표시하며 이는 실제 접수 종료 시각과 구분한다. iframe을 사용하지 않고 원문은 새 탭으로 연다.
- 열람 시 자동 읽음 처리하며 안 읽음으로 되돌릴 수 있다. 이전·다음 탐색은 안 읽은 목록의 자동 변경에도 탐색 시작 순서를 유지한다.
- 별표로 관심 공고를 등록·해제하고 관심 메뉴에서 메모·우선순위를 관리한다. 지원 준비 상태와 지원일은 별도 지원 준비 메뉴에서 관리한다. 로그인과 면접/최종 결과 단계는 범위 밖이다.

### 앱 내 뒤로·앞으로 탐색

- 브라우저의 뒤로·앞으로 동작으로 공고 모아보기·관심 공고·수집 기록·통계·AI 질문·경력 자료·마이페이지 등 주요 화면 사이를 이동할 수 있어야 한다.
- 주요 화면 전환, 공고 상세 패널과 관심 공고 상세를 별도 탐색 단계로 기록한다. 뒤로가기는 위에 열린 상세부터 닫고, 앞으로가기는 다시 연다. 상세의 이전·다음 공고 이동도 기록해 앞서 열었던 공고로 돌아갈 수 있다. 경력 자료 화면에서는 자료/추천 탭과 마지막 선택 추천 결과를 공고 상세 이동 뒤에도 복원한다.
- 변화 요약·통계·수집 기록의 공고 목록 이동과 수집 기록 펼치기도 복원한다. 공고 목록의 검색·직군·회사·읽음·마감 조건, 정렬, 페이지, 스크롤 위치를 유지한다.
- 검색·필터·정렬·페이지 크기 변경은 현재 탐색 기록에 갱신하며 각각 새 기록을 만들지 않는다. 화면·상세·기록 목적지 이동은 별도 기록으로 남긴다.
- 수집 창·관심 공고 비교·캡처 확대 모달은 뒤로가기로 먼저 닫고 앞으로가기로 다시 연다. 앱 내부 기록이 없을 때는 브라우저의 일반 뒤로가기를 가로채지 않는다.
- 브라우저 새로고침 후 현재 화면·상세·모달과 복원 가능한 목록 문맥을 유지한다. 원문 링크는 새 탭에서 열어 앱의 기록을 바꾸지 않는다.

## 수집 기록·실패·검증

- 버튼으로 시작한 실행마다 기록 하나를 남긴다. 분야·선택 회사·시각·소요 시간·전체 진행률·기업군별 성공·신규·변경·동일·실패를 표시한다.
- 목록 조회 실패로 집계할 수 없는 값은 `—`로 표시하고 실제 0건과 구분한다.
- 실패 상세에는 회사·공고명(알 수 있을 때)·URL·단계·시각·재시도 횟수·오류 원문을 표시한다.
- 실패 전체 또는 항목별로 실패 단계부터 재시도한다. 선택 분야·계열사를 유지하며 캡처 실패 시 저장된 본문을 재추출하지 않는다.
- 재시도는 원 실행과 연결된 별도 기록이다. 복구 성공 시 원 실패 기록에도 해결 여부를 반영한다. 일부 실패해도 성공한 결과는 저장한다.
- 사용자가 실제 버튼을 통한 검증을 허용했다. 표본 회사·분야 조합으로 검증하고 필요 이상의 전체 재수집과 외부 요청을 피한다. 보안 확인 화면은 공고로 보관하지 않는다.

## 채용 통계

- 여러 직군·사이트를 지원한 상태에서 별도 `채용 통계` 화면을 제공한다. 비개발은 3개 공식 사이트·12개 회사, 개발은 8개 세분화 분야를 유지한다.
- 사이트·회사·직무·미분류를 교차 필터하고 사이트/회사/직무별 비교와 공고 목록 이동을 지원한다. 전체는 URL 단위로 중복을 제거하며 다중 카테고리 행의 합계는 겹칠 수 있다.
- 현재 열린 공고·보관 마감·발견 후 경과와, 선택 기간의 신규 발견·마감·재오픈 추이를 구분한다. 한국 시간 7/30/90일 또는 최대 366일을 선택한다.
- 평균 열림 관측 기간은 열림을 처음 확인한 시각부터 마감을 처음 확인한 시각까지다. 실제 게시 기간으로 표현하지 않으며, 아직 열린 공고·최초부터 마감인 공고는 완료 평균에서 제외한다. 표본이 없으면 대기 표시, 재오픈은 새 기간으로 처리한다.
- 성공한 수집은 본문 변경 여부와 무관하게 상태 관측을 저장한다. 실패·제외는 상태를 확정하지 않는다. 기존 데이터는 마지막 상태만 기준점으로 가져오며 과거 마감/재오픈을 추정하지 않는다.
- 수집하지 않은 날은 미관측으로 드러내고 마지막 관측·미확인 공고·표본 수와 관측 간격을 표시한다. 상세 계약은 [채용 통계](statistics.md)에 둔다.

## 문서 유지

기능·지원 범위·판별 규칙·API·실행 흐름을 변경할 때 관련 문서를 함께 갱신한다. 문서별 기준 역할과 변경 영향은 [문서 안내](README.md)에 두며, 작업 지침은 루트 `AGENTS.md`를 따른다. 코드 구현 지원과 실제 수집 검증을 구분하고, 과거 검증 당시 공고 수를 현재 데이터 수로 안내하지 않는다.

## 저장 공고 자동 분류 · v0.5

모든 수집에서 제목·저장 본문만으로 21개 직군의 일반 규칙을 적용한다. 수집 버튼의 분야는 저장 태그의 정답이 아니다. 개발 세분화에 AI 응용·에이전트, ML 플랫폼/MLOps, 클라우드·시스템 인프라, DBA/데이터베이스, 임베디드·시스템 SW, 로보틱스·자율주행, QA·테스트 자동화, 데이터 분석·BI를 추가했다. 기획·전략, PM, 디자인, 마케팅, 영업·사업개발을 함께 지원한다.

복수 규칙을 통과한 공고는 여러 직군에서 조회한다. 규칙 미충족 공고는 억지로 배정하지 않고 미분류 탭에 표시한다. 규칙 버전·판정 시각·입력 해시·담당 업무 근거·미분류 이유를 저장한다. 재분류는 최신 저장 본문으로 태그를 교체하고 본문/캡처 버전을 추가하지 않는다. 기존 회사별 후보 탐색·수집 지원 범위는 유지한다. 상세 기준은 [일반 규칙](classification-rules.md), 회사 조합은 [직무 지원표](job-categories.md)가 기준이다.

2026-11-15 사용자는 구현 검증 후 기존 운영 데이터(공고·본문·캡처·수집 기록)를 초기화하고 실제 재수집은 직접 하기로 했다. 정답 스냅샷과 평가 문서는 보존한다.

## 관심 공고와 지원 후보 관리

[관심 공고 합의서](interest-postings-spec.md)를 따른다. 별표는 목록과 상세에서 변경하고 읽음과 독립적으로 저장한다. 관심 메뉴는 전체/지원 준비 전/준비 중/지원 완료 탭, 우선순위 정렬, 메모 검색, 기업군·직군·마감 필터와 상세 연속 탐색을 제공한다. 지원 상태는 읽기 전용 배지로 표시하며 마감 공고도 기본 포함한다.

메모는 5,000자까지 명시적으로 저장한다. 지원 준비 상태 변경은 지원 준비 메뉴에서만 한다. 관심 해제는 별표만 바꾸며 메모·우선순위는 보존하고 재등록하면 복원한다. 지원 건·지원일은 관심 등록과 별도 생명주기를 가진다. 원문 방문만으로 지원 완료 처리하지 않는다.

개인 정보는 원본 공고 ID당 하나이며 본문 버전/직군별로 중복 생성하지 않는다. 수집기·재분류는 해당 테이블을 쓰지 않으므로 재수집·내용 변경·마감 시 관리 정보가 유지된다. 데이터 초기화는 수행하지 않는다.

## 개인 데이터 관리와 검토 도구 (2026-11-16)

관련 상세 규칙은 [개인 데이터 관리와 공고 검토 도구](workspace-tools-spec.md)를 따른다.

- 마이페이지: 관심 관리 정보 / 수집 공고 전체 / 읽음 상태 / 프리셋 / 경력 자료 초기화, 미사용 파일 정리, ZIP 백업·복원. 관심 초기화는 관심 표시·메모·우선순위만 지우고 지원 건은 유지한다. 수집 공고 초기화에는 지원 건·문항·답변·맞춤 자료·면접 기록과 공고 의존 데이터가 포함되고 프리셋·경력 자료는 유지한다. 경력 자료 초기화는 경력 자료·추천과 지원 답변·맞춤 자료·경험 인터뷰를 지우되 지원 상태·문항은 유지한다. 확인 문구를 입력해야 실행되며 수집 중 서버에서도 차단한다.
- 상세의 변경점 비교: 저장된 이전 버전과 문장 단위 `+`/`−` diff. 기준 버전과 전체 본문 표시를 선택한다.
- 수집 프리셋: 여러 직군과 회사의 선택 조합을 저장·편집·삭제하고 한 번에 실행한다. 한 실행의 공통 큐에서 직군 합집합을 적용하며 동일 URL은 한 번만 처리한다. 회사별 지원 범위를 검증하며 전체 공고와 세부 직군의 동시 선택은 금지한다.
- 수집 후 변화 요약: 관심 공고 변경·새로 마감, 신규, 전체 변경·새로 마감의 건수와 공고 목록 링크. 관심 여부는 수집 당시 값으로 저장하며 과거 실행의 누락된 상태를 추정하지 않는다.
- 관심 공고 비교: 2~3개의 회사·근무지·본문·내 메모·지원 상태 배지를 나란히 확인한다. 비교 창을 열 때 본문을 불러오고 읽음 처리한다.
- ZIP 백업·복원: 공고·캡처·관심 정보·프리셋·기록·통계·경력 자료와 추천·맞춤 초안·공고별 지원 준비 기록을 포함한다. 검증과 건수 미리보기 후 현재 전체 데이터를 교체하며, 수집 중에는 실행할 수 없다.

이 기능 도입 시 기존 데이터를 자동 초기화하거나 외부 사이트를 자동 재수집하지 않는다. 회사·직군별 지원 범위 및 분류 규칙은 그대로 유지한다.

## 본문 없는 마감 공고 처리 (2026-11-21)

네이버·토스·당근·Greeting·Ninehire·쿠팡 공식 API의 사이트별 종료 증거를 본문 추출과 구분해 처리한다. 명시적인 접수 종료 또는 확인된 공개 종료 화면은 기존 공고만 마감 처리하고 정상 본문·캡처·개인 관리 정보를 보존한다. 단순 목록 누락·일반 404·403·429·서버 오류는 마감으로 간주하지 않는다. 실제 사이트 검증 범위·조건·제외 사례는 [사이트별 공고 마감 판별](closure-detection.md)을 따른다.

수집 기록의 마감 확인 건수는 성공 건수에 포함한다. 변화 요약의 ‘새로 마감’은 기존에 열려 있던 공고의 상태 전환만 세므로 마감 확인 건수와 구분한다. 도입 시 기존 실패나 공고 상태를 일괄 수정하지 않으며 실제 재수집은 사용자가 실행한다.

## 전체 공고 AI 질문

- 공고 상세에 붙지 않는 전역 `AI에게 질문` 화면에서 여러 대화를 만들고 다시 열거나 삭제할 수 있다. 질문은 대화와 함께 저장한다.
- 질문 POST는 대화에 사용자 메시지·빈 답변 메시지·대기 작업을 한 트랜잭션으로 저장하고 `202 Accepted`와 작업 ID를 즉시 반환한다. Codex 워커가 꺼져 있어도 대기열에 남고, 워커가 연결되면 처리한다.
- 처리는 브라우저 연결과 독립적이다. 대화 화면은 작업별 SSE를 구독해 상태·웹 검색·답변 조각을 받는다. 브라우저 연결이 끊기면 작업을 취소하지 않으며, 이벤트 ID 이후의 DB 저장 이벤트를 재생해 답변을 이어서 표시한다.
- 답변 조각과 상태 이벤트는 MySQL에 순서대로 보관한다. 완료 답변·공고 근거·웹 출처도 대화 이력에 저장한다. 워커 임대가 만료되면 작업을 다시 대기시키고 부분 답변을 비운 뒤 재시작 상태를 전달한다. 최종 처리 실패는 대화에서 재시도할 수 있다.
- AI는 모든 저장 공고의 메타데이터·직군·열림/마감 상태를 조회한다. 질문 용어와 회사·제목·직군·근무지·본문을 기준으로 관련 공고 본문 일부를 검색해 모델에 제공한다. 열림/마감 질문을 명시하면 해당 상태로 범위를 좁힌다. 현재 입력은 관련 공고 최대 12건, 본문 건당 최대 6,000자이며 전체 회사·직군별 건수 요약을 함께 전달한다.
- 질문에 저장 자료만으로 충분히 답할 수 없거나 최신·외부 정보가 필요하면 웹 검색을 수행한다. 검색 중 상태를 화면에 표시하고, 저장 공고 출처와 외부 웹 출처를 구분해 클릭할 수 있게 보여준다. 웹 검색 페이지 본문은 보관하지 않고, 답변과 출처 제목·URL·설명만 저장한다.
- 답변의 `**강조 문구**`는 굵게 렌더링한다. 본문 안의 `[공고:id]` 표시는 해당 답변에 저장된 공고 근거와 연결해 공고를 바로 열 수 있게 한다.
- 모델은 `gpt-6-luna`로 고정한다. Codex 로컬 워커는 읽기 전용 샌드박스, 셸 도구 비활성화, 웹 검색 허용으로 실행한다. 공고·읽음·관심·마감 상태를 AI가 수정하는 도구는 제공하지 않는다.
- 앱 시작 때 로컬 Codex 워커를 자동으로 시작한다. Java 21 이상·Codex CLI·CLI 로그인이 준비되지 않으면 Docker 앱은 계속 동작하고 AI 질문과 경력 자료 분석은 워커가 연결될 때까지 대기한다. 워커만 복구할 때는 `./ai-worker.sh start`를 사용한다. 수집·공고 열람·기존 데이터 관리는 워커 없이 동작한다. 상세 API·재연결 계약은 [AI 질문과 Codex 워커](ai-chat.md)를 따른다.

## 경력 자료 등록과 AI 정리

- 주 메뉴 `경력 자료`에서 이력서·포트폴리오·프로젝트 문서 등 여러 파일을 종류 구분 없이 한 번에 등록한다. 확장자나 업로드 전에 고르는 문서 종류로 처리 방식을 고정하지 않고, 파일 내용에서 형식을 감지한다.
- 원본 파일은 로컬 저장소에 보관하고 SHA-256 내용이 같은 파일은 중복으로 등록하지 않는다. 한 번에 최대 20개, 파일당 50 MiB, 요청 합계 200 MiB까지 허용한다.
- Apache Tika로 지원되는 문서의 텍스트를 추출하고 페이지·제목·문단 위치를 저장한다. 이미지 전용 문서는 설치된 한국어·영어 OCR로 읽기를 시도하지만, 파일 손상·비지원 형식·이미지 품질에 따라 텍스트를 얻지 못할 수 있다. 추출할 수 없는 경우에도 원본을 보관하고 이유를 표시한다.
- Codex 워커가 켜져 있으면 추출한 텍스트를 `gpt-6-luna`에 보내 경력·프로젝트·기술·성과·학력 후보를 비동기로 정리한다. AI 응답의 각 후보는 문서 원문에 실제 포함된 인용과 위치가 검증된 경우에만 저장한다. 저장된 후보는 별도 확정 없이 기본적으로 추천·맞춤 초안에 반영한다. 사용자는 제목·설명을 수정해 저장하거나 잘못된 후보만 제외할 수 있고, 제외한 항목은 다시 추천에 포함할 수 있다. `UNVERIFIED`와 기존 `VERIFIED` 상태는 모두 추천에 쓰며 `REJECTED`만 제외한다. 원문 근거가 있어도 AI 요약의 사실성까지 자동 검증된 것은 아니므로, 추천·초안은 원문 근거를 함께 보여주고 근거 밖의 내용을 만들어내지 않는다.
- 추천은 개수(1~20)와 선택적인 자연어 희망 방향을 받는다. 직군·회사·지역은 `상세 조건` 안에 접어 두고, 직군과 회사는 자동완성으로 여러 개 선택하며 지역은 쉼표로 구분해 입력한다. 상세 조건을 비우면 전체 열린 공고를 대상으로 한다. 선택한 직군·회사·지역은 서버에서 후보를 좁히는 조건이고, 같은 항목 안에서는 하나라도 맞으면 포함하며 서로 다른 항목은 모두 만족해야 한다.
- 자연어 희망 방향은 기본적으로 추천 우선순위에 반영한다. 사용자가 제외·회피를 명확히 적은 경우에만 해당 조건을 추천에서 제외하고, 모호한 선호를 임의의 제외 조건으로 해석하지 않는다. 저장 상태가 열린 공고만 후보로 보고 마감 공고는 제외한다. 공고·본문과 제외하지 않은 경력 정보, 입력한 희망 방향의 연관도를 바탕으로 최대 36개 후보를 AI에 전달하며, 요청한 개수까지 근거가 약하면 적은 수만 반환한다. 결과에는 적용 조건과 AI가 이해한 희망 방향을 함께 표시한다.
- 추천 결과는 숫자 점수 대신 `잘 맞음`, `검토해볼 만함`, `자료가 부족함`으로 표시한다. 공고에서 확인한 요구·자료 공백과 연결된 경력 정보, 원문 인용을 함께 보여준다. AI가 선택한 공고 ID와 경력 근거 ID는 요청에 포함된 후보 집합과 대조한다.
- 추천 공고의 `지원 준비`를 시작하면 별도 `지원 준비` 메뉴에서 해당 공고의 이력서·포트폴리오 초안, 문항별 지원서 답변, 면접 준비를 관리한다. 추천·관심 여부와 지원 건은 독립적이며 공고마다 지원 건은 하나다. 상태는 `지원 준비`와 `지원 완료`로 기록하고 실제 지원서 제출은 하지 않는다.
- 지원 건의 이력서·포트폴리오 초안은 제외하지 않은 경력 정보와 원문 인용을 근거로 삼는다. 섹션·프로젝트를 편집·포함·제외·재정렬해 해당 지원 건에 저장하며, 원본 경력 파일은 수정하지 않는다.
- 경력 자료 정리·추천·맞춤 초안은 외부 웹 검색을 사용하지 않는다. 문서 본문과 공고 본문은 지시가 아니라 분석 대상 데이터로 취급한다. 원본 파일은 로컬에 남고, 추출 텍스트·파일명은 분석 때, 제외하지 않은 경력 정보와 선택 공고 본문은 추천·초안 생성 때 외부 Codex 서비스로 전송된다.
- 워커가 꺼져 있어도 자료 등록·본문 추출·열람·삭제와 추천·초안 요청 저장은 가능하며, AI 작업은 대기 상태로 남는다. 워커는 AI 질문, 경력 자료 분석, 경력 추천·초안, 공고별 지원 준비의 네 큐를 번갈아 확인한다. 워커 운영과 재시작 확인은 [AI 질문과 Codex 워커](ai-chat.md)를 따른다.
- 원본·본문·추출 정보의 제외 상태·추천·맞춤 초안은 ZIP 백업과 `경력 자료 초기화` 범위에 포함한다. `수집 공고 초기화`도 공고에 의존하는 추천·맞춤 초안을 지운다.

API·파일 저장·큐 임대 계약은 [백엔드 문서](../backend/README.md), 화면 흐름은 [프론트 문서](../frontend/README.md)를 따른다.

## 공고별 지원서 요구 정보

- 공고 상세의 `지원서 정보` 탭은 공고 수집 실행에서 자동으로 가져온 실제 지원 페이지 원문 하나를 보여준다. 원문을 찾지 못하면 입력 칸은 비워 두고 실패 사유를 표시한다. 공고 본문에 있는 `지원하세요` 같은 안내 문장은 지원서 원문으로 사용하지 않는다.
- 지원 페이지 확인은 공고 수집 실행에 포함된 열린 공고마다 함께 시작한다. 공고 처리와 지원 페이지 확인 진행률·회사별 결과는 분리해서 표시한다. 별도의 지원 페이지 확인 버튼은 제공하지 않으며 실패한 공고는 다음 공고 수집 실행에서 다시 확인한다.
- 지원 페이지 작업자는 공개 지원 링크로 이동해 보이는 페이지 텍스트를 최대 100,000자까지 저장한다. 지원 경로를 찾지 못하면 공고 본문으로 대체하지 않고 실패 이유를 남긴다. 로그인·폼 입력·파일 업로드·동의·제출은 하지 않고 쿠키·로그인 세션·로컬 Chrome 프로필도 사용하지 않는다. HTTPS 공개 IP만 허용하며 사설·로컬 주소와 위험한 리다이렉트를 차단한다.
- 원문 입력 칸은 하나만 둔다. 사용자가 실제 지원 페이지에서 복사한 원문을 붙여넣고 수정해 저장할 수 있으며, 저장된 원문은 복사할 수 있다. 수집 실행별 확인 이력은 매번 남기되, 최신 원문 버전과 내용이 같으면 버전은 추가하지 않고 확인 이력에서 기존 버전을 참조한다. 사용자가 직접 저장할 때도 최신 버전과 같으면 새 버전을 만들지 않는다. 내용이 달라질 때만 새 버전을 추가하고 이전 원문을 보존한다. 버전 선택은 실제 원문 버전만 보여준다.
- 지원서 원문을 저장만 했을 때는 AI에 보내지 않는다. 사용자가 지원 준비 화면에서 문항 추출·답변 초안을 명시적으로 요청할 때 해당 원문, 공고, 필요한 경력 근거를 `gpt-6-luna` 워커 작업으로 전달한다. 문항을 원문 근거와 연결하고, 답변은 질문마다 따로 편집·저장하며, 답변에 사용된 경력 사실 ID를 표시한다. 모델은 경력·성과·수치를 만들지 않고, 답변 생성 결과는 제출 전 사용자가 확인하는 초안이다. 실제 지원서 제출은 하지 않는다.
- 관심 공고에는 지원 상태 배지만 표시한다. 상태 변경은 별도 지원 준비 화면에서만 하며, 지원 건을 시작하지 않은 공고는 `지원 준비 전`으로 표시한다. 공고 상세에서 `지원 준비 시작`을 누르면 이미 존재하는 해당 공고의 지원 건을 다시 연다.
- 면접 준비는 선택한 지원 건에서 요청할 때 공개 웹을 검색한다. 회사 공식 채용 안내·기술 블로그, 공개 지원자 후기, 해당 공고 기반 추론을 서로 분리하고 각 출처 URL·확인 시각·신뢰도를 보인다. 반복 경향은 서로 다른 후기 URL 2개 이상이 확인될 때만 표시한다. 출처가 적거나 날짜가 오래됐으면 낮은 신뢰도로 보이며 실제 질문을 보장하지 않는다. 질문은 공고·이력서·포트폴리오·지원서 답변·회사 경향의 다섯 근거 유형으로 나눠 표시한다.
- 경험 인터뷰는 조사 질문에 하나씩 답하고 꼬리 질문으로 역할·판단·결과를 구체화한다. 인터뷰 답변에서 정리된 경험은 후보로만 보관한다. 사용자가 내용을 확인하고 명시적으로 저장했을 때에만 근거 인용과 함께 경력 자료에 `UNVERIFIED` 후보로 추가한다.
- 지원서 답변·맞춤 자료·조사·경험 인터뷰 작업은 DB에 저장하고 즉시 작업 ID를 반환한다. 워커가 꺼져 있으면 `WAITING_AI`로 남고, 연결되면 처리한다. 브라우저를 닫아도 취소하지 않으며 화면을 다시 열면 저장된 결과와 진행 상태를 확인한다.
- 공고 삭제/초기화는 연결된 지원 건·문항·답변·자료·면접 조사와 인터뷰 기록도 삭제한다. 백업·복원에는 지원 준비 기록을 포함한다. `경력 자료 초기화`는 지원 건과 문항 질문은 남기되, 경력 근거가 필요한 맞춤 자료·지원 답변·면접 기록과 관련 AI 작업을 지운다.
- 이전 관심 공고 기능에서 저장한 `지원 완료`와 지원일은 V18 데이터 마이그레이션으로 해당 공고의 지원 건에 옮긴다. 새 상태는 지원 준비 화면을 기준으로 하며, 관심 메모·우선순위 저장은 지원 상태를 변경하지 않는다. `관심 공고 초기화`는 관심 표시·메모·우선순위만 지우고 별도 지원 건은 유지한다.
- 지원 페이지 작업은 DB 상태·임대 만료·다음 수집 실행을 통한 재시도를 사용한다. 전용 Playwright 작업자 수는 `CRAWLER_APPLICATION_PAGE_WORKERS`로 설정하며 기본값은 2다. 각 작업자는 자체 Playwright·브라우저를 생성·재사용하고, 공고 작업자와 병렬로 실행되며 사이트별 동시 요청 제한을 공유한다.
