# 관심 공고와 지원 상태 표시

기준: 2026-11-22. 관심 공고는 후보 관리, 지원 준비 공간은 실제 지원 준비 기록을 맡는다. 두 데이터는 공고 ID로 연결되지만 서로 독립적이다.

## 관심 공고에서 관리하는 정보

| 항목 | 현재 동작 |
| --- | --- |
| 관심 등록·해제 | 공고 목록·상세의 ☆/★로 등록·해제 |
| 관심 목록 | 전체 / 지원 준비 전 / 준비 중 / 지원 완료 탭, 마감 포함 기본 |
| 메모 | 공고마다 최대 5,000자 편집·저장 |
| 우선순위 | 높음 / 보통 / 낮음 / 미지정 |
| 정렬 | 우선순위 높은 순, 같은 순위는 최초 발견일 최신순; 지원일 최신순·최초 발견일 최신순 선택 가능 |
| 지원 상태 | 지원 준비 공간의 상태를 읽기 전용 배지로 표시 |
| 읽음 | 관심·지원 상태와 독립적으로 유지 |
| 비교 | 2~3개 공고의 메모·본문·직군·지원 상태를 나란히 확인 |

관심 화면은 상태만 보여준다. 지원 준비 시작·상태 변경·지원일 확인은 별도 `지원 준비` 메뉴에서 한다. 지원 준비를 시작하지 않은 공고는 `지원 준비 전`이다. 관심을 해제하거나 관심 데이터를 초기화해도 별도 지원 건·상태·답변·면접 기록은 남는다.

## 데이터 경계와 이전 상태 이관

`posting_interest`의 공고별 메모와 우선순위는 관심 기능의 데이터다. 이전 버전에서 사용하던 `application_status`와 `applied_on` 열은 백업 호환을 위해 유지하지만, 실제 지원 상태의 기준은 `application_case`다. 관심 정보 저장 API는 이 두 열을 바꾸지 않는다.

V18 마이그레이션은 이전에 `APPLIED`로 저장된 공고마다 지원 완료 상태의 지원 건을 만들고, 과거 지원일을 보존한다. 과거 `BEFORE_APPLY`는 지원 준비를 시작하지 않은 상태로 취급하여 새 지원 건을 만들지 않는다. DB 이전 마이그레이션과 달리, 스냅샷 스키마 10~17의 백업에는 지원 준비 테이블이 없으므로 복원 미리보기에서 해당 데이터가 빠짐을 알린다.

- 관심 공고 초기화: `posting_interest`를 비우며 지원 건은 유지한다.
- 수집 공고 초기화: 공고에 종속된 지원 건·문항·답변·자료·면접·지원 AI 작업도 삭제한다.
- 경력 자료 초기화: 지원 건·상태·문항 질문은 유지하고, 답변·맞춤 자료·경험 인터뷰와 관련 작업을 지운다.

## 검증 기록

2026-11-16의 과거 검증은 당시 관심 화면에서 지원 상태와 지원일도 편집하던 이전 구조에 대한 기록이다. 2026-11-22 지원 준비 공간 분리 후의 동작과 혼동하지 않는다.

2026-11-22 격리 검증: V18 적용과 이전 `APPLIED` 날짜 이관, 공고당 지원 건 멱등 생성, 상태 변경, 문항·답변 저장, 관심 상태 배지와 읽기 전용 경계를 확인했다. ZIP 스키마 18에 지원 건·문항·작업이 포함되고, 관심 초기화 후에도 지원 기록이 유지됐다. 경력 자료 초기화는 가상 자료·답변·맞춤 초안을 지우고 지원 건·상태·문항을 유지했다. 가상 경력 근거로 `gpt-6-luna`의 문항 답변 및 맞춤 이력서·포트폴리오 생성을 실행해 fact ID·인용을 확인했다. 경험 인터뷰 꼬리 질문과 사용자가 승인한 `UNVERIFIED` 경력 자료 저장, 답변 근거 보존을 확인했다. 별도 가상 `Toss / Backend Engineer` 건으로 면접 검색을 한 번 실행해 공식 자료 3건·개별 후기 1건·공고 추론 3건·질문 4개를 저장하고, 반복 경향 1건에 서로 다른 후기 URL 3개가 연결됨을 확인했다. 첫 검증에서 인터뷰 승인 자료의 evidence 누락을 발견해 저장 경로를 수정하고 재검증했다. 지원 화면은 임시 Docker API·브라우저에서 맞춤 자료 편집·상태 변경·관심 배지를 확인했다. 실제 공고 수집·운영 데이터 변경·지원서 제출은 하지 않았다.
