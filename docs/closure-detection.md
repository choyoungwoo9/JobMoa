# 사이트별 공고 마감 판별

기준: 2026-11-21. 수집 실행 `1234a944-655c-4e9e-b1ad-2593a32228c3`의 실패 기록을 읽고 대표 URL을 Chrome/Playwright로 확인했다. 확인 당시 공고 작업 실패는 61건이며, 429인 25건을 제외한 36건을 사이트·오류 유형별로 묶었다. 별도로 오늘의집 목록 실패 1건이 있었다. 이 수치는 해당 실행의 스냅샷이며 현재 데이터 건수가 아니다. 모든 실패 URL을 다시 방문하지 않았다.

쿠팡 원문 대표 URL은 이번 확인에서 429 보안 확인 화면이 나와 같은 도메인의 추가 방문을 중단했다. 이에 원문 페이지 방문을 줄이기 위해 공식 상세 API 본문을 먼저 읽도록 변경했다. 본문이 기존 최신 버전과 같으면 저장된 캡처를 재사용해 원문을 열지 않는다. 신규·변경 공고는 여전히 원문 페이지가 정상 접근되고 API 본문과 화면이 일치해야 캡처된다. API 자체에서 발생한 접근 제한은 실패로 남기며, 원문 렌더링 실패였던 별도 공고의 실제 마감 여부도 단정하지 않는다.

이 변경은 429 회피를 보장하지 않는다. 변경 시점에 확인된 429의 응답 헤더와 발생 임계값은 없으며, 2026-11-21 기준 설정한 `boards-api.greenhouse.io` 3초·`www.coupang.jobs` 5초 간격은 요청 시작을 분산하는 보수적 시작값이다. 상세 API도 차단될 수 있으므로 성공률·429 재발 여부는 사용자가 소량 수집으로 확인해야 한다.

### 쿠팡 Cloudflare 응답 재확인 (2026-11-21)

대표 원문 `https://www.coupang.jobs/en/jobs/?gh_jid=8384816`를 브라우저에서 한 번 탐색했을 때 HTTP 429와 `보안 확인 수행 중` Cloudflare 화면을 확인했다. 이 브라우저 응답의 헤더는 당시 보존하지 못했다. 이후 같은 URL에 단일 진단 GET을 보냈고, 별도의 HTTP 403 응답에서 `server: cloudflare`, `cf-mitigated: challenge`, `cf-ray: a5dbab18fcdddd08-ICN`을 확인했다. 이 403 응답에는 `Retry-After`가 없었다. Cloudflare 문서에 따르면 `cf-mitigated: challenge`는 원래 요청 대상 대신 Challenge Page가 반환됐음을 뜻한다 ([공식 문서](https://developers.cloudflare.com/cloudflare-challenges/challenge-types/challenge-pages/detect-response/)).

브라우저 429와 진단 GET 403은 서로 다른 요청에서 관측한 응답이다. 따라서 Cloudflare Challenge가 응답을 가로막고 있음은 확인했지만, 앞선 429의 `Retry-After` 유무나 차단 원인이 요청 빈도·IP 평판·브라우저 검증 중 무엇인지는 판별하지 못했다. 브라우저 페이지 요청 한 번과 진단 GET 한 번만 수행했으며, 700ms 간격 반복 요청이나 추가 공고 탐색은 하지 않았다.

이후 같은 URL을 Playwright로 실행한 Chrome에서 한 번 탐색했을 때는 HTTP 200, `server: cloudflare`, `cf-ray`가 반환됐고 `cf-mitigated`는 없었다. 제목은 `Jobs | Coupang Careers`였으며 DOMContentLoaded 시점의 본문은 공고 목록(`Showing 1 to 20 of 676 matching jobs`)이었다. 이는 원문 사이트가 항상 차단되는 상태는 아님을 보여주지만, 상세 패널의 본문·캡처 완료까지 확인한 것은 아니다. 한 번의 요청 결과이며 700ms 간격 반복 요청이나 실제 수집 실행은 하지 않아, 이전 429의 원인이나 재발률은 여전히 확인되지 않았다.

Greeting 종료 컴포넌트 해석은 같은 플랫폼을 사용하는 카카오 Greeting 포털에도 연결했고, Ninehire 규칙은 카카오스타일에도 연결했다. 이 플랫폼 재사용 경로가 이번에 모두 실제 사이트 검증된 것은 아니다. 당근서비스·해외 포털, LINE/LY, 우아한형제들 등 다른 경로의 기존 마감일·상태 판별은 유지한다. 기존 직군·회사 지원 범위와 직군 분류 규칙은 변경하지 않는다.

## 처리 흐름

1. 목록 탐색은 기존처럼 HTTP 오류 시 실패한다. 공고 상세 페이지 탐색에만 404·410 응답 화면을 살펴볼 기회를 준다. 쿠팡은 공개 상세 API의 해당 공고 ID에 대한 정확한 `Job not found` 404 JSON도 마감 증거다. 403·429·5xx는 계속 실패한다.
2. `RecruitmentSite.closureReason()`에서 사이트별 종료 증거를 확인한다. 늦게 발생하는 클라이언트 이동·알림을 위해 본문 추출 예외 뒤에도 한 번 재확인한다. HTTP 오류 자체나 직군 제외를 종료 증거로 바꾸지 않는다.
3. 확정한 종료는 `PostingClosed`를 통해 공통 저장 경로로 전달한다. 기존 공고가 있으면 `closed=true`, 마지막 확인 시각과 관측·변화 기록을 같은 트랜잭션으로 갱신한다.
4. 작업 결과는 `COMPLETED/CLOSED`다. 수집 실패나 ‘내용 동일’로 섞지 않는다. 판별 근거는 작업의 진단 메시지(`error`)에 저장하고, 원래 실패의 재시도인 경우 정상 완료와 동일하게 상위 실패 해결 시각을 기록한다.
5. 정상 본문·캡처·버전·읽음·관심 표시·메모·지원 기록은 유지한다. 종료 안내/404 화면을 새 공고 본문이나 캡처로 저장하지 않는다. 기존에 저장되지 않은 공고의 종료 화면은 `EXCLUDED`로 완료하고 가짜 공고를 생성하지 않는다.
6. 정상 본문을 추출할 수 있는 공고는 기존의 마감 상태·마감일 추출 및 본문 해시 비교·버전 저장 경로를 유지한다. 목록에서 누락됐다는 사실만으로 마감 처리하지 않는다.

수집 기록의 **마감 확인**은 해당 실행에서 성공적으로 마감을 확인한 공고 수다. 기존 상태에서 새로 마감된 공고만 세는 변화 요약의 **새로 마감**과는 의미가 다르다. 마감 확인은 성공 건수의 부분집합이며, 본문을 정상 추출한 경우에는 변경·동일과 중복될 수 있다. 종료 화면만 확인한 작업은 전용 결과 CLOSED로 기록한다.

새 결과값 `CLOSED`를 포함한 백업은 형식 v2/DB 스키마 10으로 내보낸다. 현재 앱은 기존 v1과 v2를 복원할 수 있고, 이전 앱이 새 결과값을 잘못 복원하지 않도록 형식 번호를 구분한다.

## 오늘의집 목록 실패의 별도 원인

공식 Gatsby 목록에 `name=""`, `recruitUrl=null`, `teamName="MD"`, `slug="/careers/2026-11-19"`인 작성 중 메타 항목이 있었다. 제목과 지원 URL이 **둘 다 빈 경우만** 공고가 아닌 항목으로 건너뛴다. URL이 있는데 제목이 없거나 지원하지 않는 주소가 있으면 계속 오류로 드러낸다. 전체 목록 실패를 마감으로 바꾸지 않는다.

## 검증 범위

- 위 대표 사이트의 실제 화면·SSR 데이터·네이티브 알림과 공식 Greenhouse 오류 JSON을 확인했다. 추가 대량 수집이나 429 재시도는 하지 않았다.
- 캡처한 실제 HTML/SSR을 모든 외부 요청이 차단된 Playwright 환경에 재현해 양성 및 오판 방지 사례를 확인했다. 다른 공고 ID·호스트, 일반 404, 403/429/500, 다른 알림은 마감으로 처리되지 않았다.
- 실제 `BrowserSession`을 localhost 응답에 연결해 공고 404/410 화면 확인, 목록 404와 공고 403/429/500 실패, alert 수집을 검증했다.
- 임시 MySQL과 크롤러를 끈 Spring 컨텍스트에서 마감 저장·관측·관심 공고 변화 집계, 기존 버전/캡처 경로/관리 정보 보존, 미저장 종료 공고 제외 및 `CLOSED`를 포함한 v2 백업 생성을 확인했다.
- 백엔드 컴파일·프론트 프로덕션 빌드를 확인했다. 정식 테스트 소스는 추가하지 않았다.
- 2026-11-21 쿠팡 API 우선 흐름과 호스트별 간격을 구현하고 백엔드 `compileKotlin`을 통과했다. 실제 사이트 수집, 신규·변경 캡처 및 429 재발 여부는 검증하지 않았다.
- 실제 수집 실행 및 실패 재시도에 의한 최종 검증은 사용자가 수행한다. 기존 실패 기록을 직접 덮어쓰거나 공고를 일괄 마감 처리하지 않는다.

Docker 반영 후 `/actuator/health`의 UP, 백엔드·프론트 healthy, 배포된 백업 형식 v2 및 수집 기록 표의 ‘마감 확인’ 열과 설명을 읽기 전용으로 확인했다. 적용 전후 공고·버전·읽음·관심 정보와 기존 실행 기록이 동일하며 새 실행이 생성되지 않았음을 API 응답으로 비교했다. 실제 수집·실패 재시도 버튼은 누르지 않았다. 임시 DB·브라우저 검증 세션은 정리했다.
