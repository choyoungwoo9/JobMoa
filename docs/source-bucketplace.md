# 오늘의집 수집기

## 공식 출처와 수집 경로

- 공식 회사 채용 페이지: <https://www.bucketplace.com/careers/>
- 위 페이지가 사용하는 Gatsby 공개 데이터: <https://www.bucketplace.com/page-data/careers/page-data.json>
- 공식 목록에서 직접 연결한 상세 예시: <https://bucketplace.career.greetinghr.com/ko/o/216240>

2026-11-14 확인한 목록 데이터의 `result.data.position.nodes`에는 한국어 페이지 공고 67개, `positionJp.nodes`에는 일본어 공고 1개가 있었다. 각 항목의 `frontmatter`에는 `name`, `teamName`, `isPool`, `recruitUrl`, `region`이 있다. 목록의 검색 필터나 화면에 보이는 일부 카드에 의존하지 않고 두 목록의 전체 메타데이터를 읽는다.

상세는 공식 목록이 연결한 Greeting의 `bucketplace.career.greetinghr.com` 호스트에서만 읽는다. 허용 경로는 `/ko/o/{숫자 ID}` 및 실제 공식 목록에 있는 `/o/{숫자 ID}`이며, 저장 URL은 `/ko/o/{ID}`로 통일한다. 사용자 정보·추가 포트·쿼리·프래그먼트·지원서 경로 및 다른 Greeting 워크스페이스는 허용하지 않는다.

## 지원 범위

`sourceId = bucketplace`, `SourceDefinition.name = 오늘의집`이다. 회사명은 공식 상세 `groupInfo.name`에서 확인한 `오늘의집`을 사용한다. 공식 표기가 `Bucketplace`·`버킷플레이스`이면 같은 회사로 정규화한다. 이 별칭은 `CompanyRegistry`에도 등록돼 있어, 목록 호스트(`www.bucketplace.com`)와 상세 호스트(Greeting)가 다른 경우에도 회사 이름으로 식별한다.

목록 후보 규칙은 개발 직군 전용이 아니다. 명확한 소프트웨어·웹·모바일·데이터·ML·DevOps/SRE/클라우드 엔지니어 직함과 기획·PM/PO·디자인·마케팅·영업 직함을 허용한다. `all`은 이 수집기가 지원하는 직무 전체를 수집하고, 특정 분야를 선택한 실행은 `CategoryClassifier`의 오늘의집 회사별 후보·본문 규칙을 추가 적용한다. 제목만으로 애매한 직무를 특정 분야에 강제로 배정하지 않는다.

공식 팀명 `경영지원`, `물류/배송`, `정보보안`은 이번 범위에서 제외한다. HR·재무·회계·총무, 물류 운영·입출고·배송 운영, 일반 고객상담/지원, 인재풀, QA·Scientist·Analyst·Security 직함도 제외한다. `Engineering` 팀의 `Data Analytics Engineer`와 재무 분석가인 `Data Analyst (Finance)`는 구분한다.

공식 목록에는 `[오늘의집시공]` 접두사가 있는 영업·디자인 공고도 있다. 이는 원문 직함에 그대로 보존한다. 이번 상세 표본에서 별도 법인명은 확인하지 않았으므로 새 계열사를 추정해 만들지 않는다. 다른 공식 회사명이 상세 메타데이터에 나온 경우 그 이름을 보존한다.

## 상세 본문과 캡처

Greeting의 `#__NEXT_DATA__` 내 `getOpeningById` 응답이 성공했는지, 공고 ID가 URL과 일치하는지 확인한다. 본문은 실제 보이는 `.ql-editor`에서 읽고, 다음 조건을 모두 확인한다.

- 브라우저 문서 제목·실제 페이지 제목이 공식 상세 공고명과 일치한다.
- 공식 `openingsInfo.detail`의 본문 시작 부분이 보이는 에디터 본문과 일치한다.
- 본문이 100자 이상이고 화면에 정상 렌더링돼 있다.

오류·보안 확인 화면은 이 조건을 통과하지 못해 실패로 기록된다. 숨겨진 중복 에디터와 지원자 개인정보 동의·추천·지원 폼 영역은 본문에 넣지 않는다. 제로폭 문자와 과도한 공백을 정리해 본문의 의미와 무관한 차이를 줄인다. 상태와 공식 마감일로 마감 여부를 판단한다. `openingsInfo.deploy`는 실제 열린 상세에서도 `false`였으므로 마감 판단에 사용하지 않는다.

캡처 재시도에서도 동일한 상세 검증과 저장 본문 제목 일치 검증을 수행한다. 수집기는 공용 큐의 `BrowserPage`만 사용한다. 별도 브라우저·작업자·DB 저장 코드를 만들지 않는다.

## 검증 범위와 호출량

- 공식 목록 페이지 한 세트와 위 상세 공고 1개만 확인했다. 다른 상세 공고를 연속 조회하거나 별도 수집 실행을 만들지 않았다.
- 목록 메타데이터는 `/tmp/jobmoa-bucketplace-list.json`에, 상세 표본은 `/tmp/jobmoa-bucketplace-detail.json`에 저장해 추가 요청 없이 분석했다.
- 표본 `Senior Backend Engineer, Commerce`는 `OPEN`, 공식 회사명은 `오늘의집`, 실제 보이는 본문은 원문 기준 3,521자였다. 정규화 후 3,421자의 본문과 화면 일치 검증에 성공했고 전체 페이지 캡처도 확인했다.
- 표본 페이지는 별도 내부 스크롤 없이 문서 전체 높이 3,827px로 표시됐다.
- Kotlin 메인 컴파일을 통과했다. 수집 실행 및 분야별 추가 본문 검증은 루트 작업에서 소량으로 수행한다.

목록의 명확한 직함 기준으로 PM/PO 3개, 서비스·사업 기획 0개(별도 상품기획 MD 1개), 디자인 5개, 마케팅 5개, 영업 6개가 관찰됐다. 분야 간 중복 직함이 있으므로 합산 값은 고유 공고 수가 아니다. 실제 분야별 저장 여부는 본문 규칙까지 통과한 결과로 결정된다.
