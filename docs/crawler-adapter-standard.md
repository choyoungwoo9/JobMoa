# 크롤러 어댑터 표준

새 채용 사이트를 추가하거나 기존 어댑터의 동작을 바꿀 때 공통 처리와 사이트별 규칙의 경계를 지키기 위한 개발 기준이다. 현재 코드 구조에 맞춘 기준이며, 구현 여부와 실제 사이트 검증 여부는 별도로 기록한다.

프로젝트 전체 문서의 역할·변경 영향은 [문서 안내](README.md)를 기준으로 한다. 이 문서는 크롤러 변경에 필요한 세부 절차를 보충한다.

## 책임 경계

| 영역 | 책임 | 기준 위치 |
| --- | --- | --- |
| 공통 실행부 | 공통 큐, 작업자 선점·임대, 사이트별 동시성, 단계별 재시도, 본문·캡처 중복 저장 방지, 결과 저장 | `CrawlerRuntime`, `CollectionService`, `TaskService` |
| 사이트 어댑터 | 목록 탐색, URL 허용·정규화, 사이트 응답 해석, 본문 추출, 캡처 준비, 사이트 고유 마감 증거 | `RecruitmentSite` 구현체 |
| 회사 카탈로그 | 포털에 속한 회사·별칭·회사별 지원 직군 | `CompanyRegistry` |
| 직군 판정 | 추출된 본문을 직군 기준에 연결하고 복수 직군 허용 | `CategoryClassifier`, 분류 규칙 |
| 문서 | 제품 범위·판정 근거·구현 및 실제 검증 범위 | 아래 문서 변경표 |

어댑터는 기업별 작업자, 별도 큐, 자체 저장소나 공통 실행 흐름을 만들지 않는다. 사이트나 계열사마다 목록·본문·마감 방식이 다르면 어댑터 또는 그 내부 포털 전략으로 표현한다. 공통 런타임에 특정 사이트의 키워드 필터나 페이지 선택자를 넣지 않는다.

## 공통 계약

어댑터는 `RecruitmentSite`를 구현한다. 공통 계약의 입력·출력은 `DiscoveredPosting`과 `ExtractedPosting`이다.

- `definition`: 사이트/기업군의 식별자와 기본 목록 URL. `SourceRegistry`에도 등록한다.
- `discoveryTargets`: 통합 어댑터가 담당하는 회사별 목록 포털. 포털마다 고유 ID·이름·목록 URL을 둔다.
- `discoverAt`: 지정된 목록에서 후보를 찾고, 제목·회사·근무지·상세 URL이 확인된 공고를 `emit`한다. 정상적인 0건과 목록 조회 실패를 구분한다.
- `canonicalizeUrl` / `acceptsUrl`: 추적용 파라미터 등 중복을 만드는 URL 차이를 정리하고, HTTPS·허용 호스트·상세 경로만 허용한다. 큐 등록과 실패 재시도에서 모두 검증되므로 외부 호스트나 임의 경로를 허용하지 않는다.
- `extract`: 상세 페이지에서 제목·회사·근무지·본문을 추출한다. 필수 정보를 임의의 기본값으로 채우거나 목록 제목만 본문처럼 저장하지 않는다.
- `closureReason`: 사이트가 제공하는 명시적 종료 증거만 반환한다. 일반 HTTP 오류 하나만으로 마감을 추정하지 않는다.
- `prepareCapture`: 캡처 전에 동의 배너·고정 오버레이 등 사이트 고유 처리가 꼭 필요할 때만 적용한다. 공통 저장 단계에서 실제 상세 화면을 캡처한다.
- `requiresWindowedBrowser`: 사이트가 화면 모드를 요구할 때만 켠다. Playwright·브라우저의 생성과 재사용은 작업자 소유다.

기본 처리 순서는 **목록 조회 → URL 정규화·허용 검사 → 공통 큐 등록 → 상세 페이지 탐색 → 사이트별 마감 확인 → 본문 추출·분야 판정 → 변경 여부 확인 → 필요한 경우 캡처 → 공통 저장**이다. 본문 추출과 캡처는 서로 다른 체크포인트이므로, 캡처 재시도 때문에 본문을 다시 추출하지 않도록 공통 실행부의 단계를 유지한다.

## 신규 사이트 구현 순서

1. **대상과 출처를 정한다.** 공식 채용 사이트/API, 포털, 소속 회사, 지원하려는 직군, 지역 범위와 제외 대상을 적는다. 통합 포털의 계열사를 포털 이름과 같은 회사로 뭉뚱그리지 않는다.
2. **사이트 구조를 확인한다.** 목록과 대표 상세 페이지를 실제 브라우저로 살펴 목록 데이터의 출처(API/HTML), 페이지 이동, 상세 본문, 접근 제한, 종료 표시를 확인한다. 확인한 URL과 날짜를 남긴다. 403·429·보안 확인을 우회하지 않고 실패 조건으로 기록한다.
3. **어댑터를 만든다.** 사이트별 네트워크·DOM 규칙은 어댑터에 둔다. 공통 인터페이스를 통해 발견 공고와 추출 공고를 반환하고, 공식 API를 쓰면 페이지의 제목·본문과 식별 정보를 대조한다.
4. **등록을 연결한다.** `SourceRegistry`에 사이트를 추가하고 `CompanyRegistry`에 회사 ID·source ID·portal ID·공식 표기 별칭·지원 직군을 연결한다. 포털 ID는 실제 `discoveryTargets`에 있어야 한다. 한 공고가 여러 직군에 해당할 수 있으며 `all`은 저장 직군 태그로 취급하지 않는다.
5. **후보 선별과 직군 판정을 분리한다.** 사이트 공식 직군·포털 필드로 후보를 줄이는 로직은 어댑터에 둔다. 추출한 공고를 회사×직군에 최종 매핑하는 규칙은 `CategoryClassifier` 및 분류 규칙에 둔다. 본문에 특정 단어가 있다는 이유만으로 공통 후보 필터를 추가하지 않는다.
6. **종료·오류 상태를 확인한다.** 사이트가 명시적으로 마감을 표현하는 UI/API/상태를 식별한다. 신호가 불충분하면 열림이나 마감으로 단정하지 않고 작업 실패로 남긴다. 성공·제외·마감·실패의 차이는 아래 기준을 따른다.
7. **표본 범위로 확인한다.** 목록이 정상적으로 0건을 반환하는 경우, 실제 공고 후보, 종료 공고 또는 이에 해당하는 격리 픽스처를 확인한다. 지원 전체 범위를 확인한 것처럼 표현하지 않는다. 외부 사이트 요청은 작은 회사/분야 조합으로 제한하고 전체 반복 수집을 피한다.
8. **문서를 함께 갱신하고 검토 가능한 커밋으로 묶는다.** 변경표에 해당하는 문서와 코드·설정 변경을 같은 작업에 포함한다. 실제 수집 검증을 사용자가 직접 하겠다고 지정한 경우 수집 실행과 실패 재시도를 시작하지 않는다.

2026-11-21 추가한 쏘카·컬리·무신사·야놀자·리디·채널코퍼레이션·여기어때·뱅크샐러드·직방도 이 절차를 따른다. 회사별 현재 규칙과 실제 접근 확인은 [사이트별 문서 인덱스](README.md#수집기와-지원-범위)에서 확인한다. 여기어때의 403 및 야놀자의 비어 있는 브라우저 화면은 성공으로 간주하지 않으며, 실제 수집 버튼을 사용하지 않았다.

## 상태를 구분하는 기준

| 결과 | 의미 | 예시 |
| --- | --- | --- |
| 성공 | 공고 본문을 확인해 저장하거나 기존 내용과 동일함을 확인 | 신규·변경·동일 |
| 제외 | 사이트/선택 분야 규칙에 따라 대상이 아님을 확인 | 인재풀, 미지원 공고 형식 |
| 마감 | 기존 공고에 대해 사이트의 명시적 종료 증거를 확인 | 접수 종료 문구, 검증된 종료 화면/API 상태 |
| 실패 | 사이트 상태나 공고 내용을 확정할 수 없음 | 403·429·5xx, 구조 변경, 필수 본문 누락, 근거가 약한 404 |

마감 처리 시 기존 정상 본문·캡처·관심 정보는 보존한다. 목록에서 사라진 사실, 리다이렉트, 접근 제한, 일반 404/410만으로 마감을 처리하지 않는다. 사이트별 예외는 [사이트별 공고 마감 판별](closure-detection.md)에 기록한다.

## 크롤러 변경 시 문서 갱신표

프로젝트 전체 변경 영향표는 [문서 안내](README.md)를 따른다. 크롤러 규칙 문서는 코드의 주석을 복제하는 대신 **왜 그 규칙이 있는지, 지원 범위가 어디까지인지, 실제로 무엇을 확인했는지**를 남긴다.

| 변경 내용 | 함께 확인·갱신할 문서 |
| --- | --- |
| 회사·계열사·포털·직군 지원 조합 또는 포함·제외 기준 변경 | `job-categories.md`, `crawler-selection-rules.md`, 해당 사이트·회사 규칙 문서 |
| 목록 후보 조건·페이지 탐색·URL·본문 추출·캡처 준비 변경 | 해당 사이트 문서. 회사/직군 범위도 바뀌면 직무 지원표와 판별 규칙 문서 |
| 사이트별 종료 증거·마감 판단 변경 | `closure-detection.md`, 해당 사이트 문서 |
| 큐·체크포인트·재시도·동시성·저장·브라우저 소유권 변경 | `backend/README.md`; 제품 동작 변화는 문서 안내의 공통 영향표도 확인 |
| 실제 사이트 검증 결과 변경 | 해당 사이트 문서에 날짜, 확인한 URL/회사/분야, 결과와 미확인 범위 |

지원 조합의 기계적인 현재 값은 `SourceRegistry`·`CompanyRegistry` 등 코드가 기준이다. 문서에는 그 값을 다시 무근거로 복사하지 않고, 실제 지원 범위의 설명·제외 이유·검증 범위를 남긴다. 코드와 문서가 달라지면 변경을 마무리하기 전에 양쪽을 맞춘다.

실제 검증 기록은 과거 결과임을 날짜로 표시한다. 확인 당시 공고 건수를 현재 데이터 수처럼 쓰지 않으며, 구현 지원과 브라우저에서 성공을 확인한 범위를 구분한다.

## 사이트별 문서 템플릿

기존 사이트 문서가 없으면 `docs/source-{source-id}.md`를 만들고 아래 항목을 기록한다. 기존 문서가 있으면 새 문서를 중복 생성하지 말고 해당 문서 구조를 보완한다.

```markdown
# {사이트/기업군} 수집 규칙

## 포털과 지원 범위
- 공식 목록/API:
- 포털 및 소속 회사:
- 구현한 직군과 제외 범위:

## 목록 후보 규칙
- 목록 데이터 출처와 페이지 이동:
- 후보 포함·제외 근거:
- 정상 0건과 실패 구분:

## 상세 페이지
- 허용 호스트·URL 형식:
- 제목·회사·근무지·본문 추출:
- 캡처 전 사이트별 처리:
- 마감 증거와 오탐 방지 조건:
- 403·429·일반 404 등의 처리:

## 실제 확인 범위
| 날짜 | 회사/직군·대표 URL | 확인한 동작 | 결과와 미확인 범위 |
| --- | --- | --- | --- |
```

현재 구현 목록과 직군 판별의 전체 기준은 [수집·선별 규칙](crawler-selection-rules.md), 회사×직군 지원 조합은 [직무 지원표](job-categories.md), 공통 수집 저장 동작은 [백엔드 안내](../backend/README.md)에 둔다.
