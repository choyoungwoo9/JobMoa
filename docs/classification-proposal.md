# 직군 자동 분류 기준 제안 — 440개 저장 공고 검토

**상태: 사용자 승인 대기. 현재 제품 동작을 설명하는 확정 스펙이 아니다.**

사용자가 요청한 순서는 **저장된 440개 전수 분석 → 기준 확인 → 승인 후 구현**이다. 이 작업에서는 분석 자료와 문서만 작성했다. 애플리케이션 코드, DB의 직군 연결, 수집기, 화면, 운영 중인 컨테이너를 변경하지 않았다.

## 분석 대상과 결과

2026-11-15 MySQL에 저장된 **공고 440개 각각의 최신 본문**을 제목·포지션 설명·담당 업무·필요 역량과 함께 검토했다. 본문 440개 모두 내용이 있으며 합계 1,262,580자다. 저장 본문에 포함된 한국어·영어·일본어·중국어를 검토했다. 외부 사이트를 재수집하지 않았다. 현재 모델에는 정형화된 공식 직군 메타데이터가 별도로 저장되어 있지 않아, 440개 모두의 공식 목록 분류까지 확보한 분석으로 안내하지 않는다.

[공고별 440행 검토표](analysis/classification-440-2026-11-15.md)에는 현재 분야, 제안 분야, 판별 이유, 저장 본문에서 가져온 짧은 근거와 원문 링크를 기록했다. [전체 JSON](analysis/classification-440-2026-11-15.json)은 공고 ID·저장 버전 ID·본문 SHA-256·보류 후보도 포함한다. 같은 제목이어도 공고 ID/URL이 다르면 각각 분석했다.

## 11개만 연결된 원인

1. `TaskService.finish()`가 선택한 `task.categoryId` 하나만 연결한다. `all`이면 연결할 분야를 비워 두므로 **전체 수집은 직군 분류를 하지 않는다.** 따라서 현재의 429개 미분류를 분류기가 429개 모두 판별 실패한 것으로 해석하면 안 된다.
2. 현재 `CategoryClassifier`는 제목이 먼저 일치해야 본문을 확인한다. 일반 Software Engineer·Node.js Developer 같은 직함은 업무가 명확해도 놓칠 수 있다. 풀스택과 백엔드/프론트엔드를 상호 배제하는 등 복수 매핑에도 맞지 않는 규칙이 있다.
3. 기존 13직군에는 MLOps·인프라·DBA·임베디드 등 실제 저장된 직무를 담을 칸이 없다.
4. DB의 `posting_category`와 도메인 `Set<String>`은 이미 공고-직군 다대다를 표현할 수 있다. 새 DB를 만들 필요가 아니라, 연결을 결정하는 동작과 화면을 고쳐야 한다.

## 공통 판별 원칙

### 수집 범위와 분류를 분리

- 전체/분야 수집 선택은 **어디에서 무엇을 탐색할지** 정한다. 선택한 버튼을 직군 정답으로 저장하지 않는다.
- 전체 수집으로 저장한 공고도 모든 지원 직군에 대해 분류한다. 분야 수집에서 저장하는 공고에는 선택 분야와 일치하는지 확인하고, 다른 직군도 업무 근거가 있으면 함께 연결한다.
- 회사×분야별 목록 탐색·공식 분류·직함 별칭은 계속 회사별 규칙으로 유지한다. 모든 회사에 ‘개발’ 한 단어 검색 같은 동일한 수집 조건을 강제하지 않는다.
- **수집 지원 회사 조합과 저장 데이터의 분류 가능 범위는 다르다.** 네이버랩스의 저장된 로봇 공고를 로보틱스로 분류할 수 있어도, 그 회사×분야의 선택 수집을 실사이트 검증했다고 표시하지 않는다. 새 8직군의 회사별 수집 지원은 어댑터별로 따로 확인해야 한다.

### 해당 지원자가 만드는 산출물을 우선

1. 공식 목록에 세부 직군이 제공되면 참고하고, 회사별 직함 표현을 해석한다. Engineering 같은 넓은 조직명은 단독 근거가 될 수 없다.
2. 포지션 설명과 **담당 업무의 대상·행위·산출물**을 확인한다. 예: ‘API 설계·구현’, ‘학습 모델 개발’, ‘DB 백업/복구 운영’.
3. 필요한 기술/경력은 업무 해석을 보강한다. 우대사항에만 있는 기술로 새 직군을 만들지 않는다.
4. 제목과 구체적 업무가 충돌하면 구체적 업무를 우선한다. 다만 특정 분야를 추가할 근거가 충돌/부족하면 그 추가 태그는 보류한다.
5. 기술 이름만 있거나 ‘협업한다’, ‘관심 있다’, ‘써 본 경험 우대’, ‘필요하면 향후 참여’ 수준이면 그 분야를 붙이지 않는다. 회사 소개, 다른 팀 소개, 관련 채용공고, 인터뷰, 복지/지원 안내도 직군 근거에서 제외한다.
6. 한국어·영어·일본어·중국어, 회사 고유 직함, 대소문자/기호 차이와 확인된 오탈자도 해석한다. 명칭의 번역만으로 업무까지 같다고 가정하지 않는다.

### 복수 매핑

- 각 직군의 포함 조건을 **독립적으로 충족**해야 붙인다. 한 직군의 단어가 다른 직군 제목에 들어 있다는 이유로 포함/배제하지 않는다.
- 웹 양쪽을 실제 구현하는 풀스택은 `풀스택 + 웹 백엔드 + 프론트엔드`에 연결한다. 제목이 일반 Software Engineer여도 본문이 양쪽을 명시하면 동일하게 처리한다.
- 한 공고가 ‘프론트 또는 백엔드 배치’, ‘Android 또는 iOS SDK’처럼 여러 경로를 명시하면 해당 경로 모두에서 조회된다. 상세에는 **선택 배치형**임을 설명한다. 이 경우 모든 영역을 동시에 맡는다고 표시하거나 풀스택을 자동 추가하지 않는다.
- 데이터 파이프라인과 백엔드 API처럼 독립된 업무가 각각 명시되면 두 분야를 연결한다. 모델 개발자가 자신의 학습 데이터를 준비하고 배포하는 통상적인 일만으로 DE/MLOps까지 자동 확장하지 않는다.
- PM의 통상적인 기획, 디자이너의 전략 수립, 개발자의 테스트 작성, 영업의 세일즈 계획 등을 전부 다른 직군으로 확대하지 않는다.
- 업무상 근거가 있는 직군만 표시하며 임의로 주직군 하나를 강제하지 않는다. 분류 이유와 선택 배치 여부를 함께 남긴다.

## 직군별 포함·제외 기준과 검토 건수

## 미분류 처리와 목록 탭

확장안에서 미분류로 남기는 공고는 **657 오늘의집 ‘오프라인 세일즈 매니저 (계약직)’ 1개**다. 주요 업무가 소품 파트너의 매입 조건 협상·발주·입고 추적·정산이어서 구매/MD 운영에 가깝다. 영업이라고 단정해 분류율을 100%로 만들지 않는다. 사용자가 구매·MD/운영을 지원 범위에 추가하면 해당 분야를 따로 정의한 뒤 연결할 수 있다.

미분류는 불필요한 공고를 삭제하는 상태가 아니라 **활성 직군 연결이 0개인 공고**다. 현재 확실한 분야가 있으면 그 분야는 유지하고, 추가 후보만 보류할 수 있다. 제안하는 미분류 사유는 다음과 같다.

- `UNSUPPORTED_ROLE`: 담당 업무는 명확하지만 지원하는 직군에 없음. 현재 657이 해당.
- `INSUFFICIENT_EVIDENCE`: 세부 직군을 정할 만큼 업무 근거가 없음.
- `CONFLICTING_EVIDENCE`: 제목·공식 분류·실제 업무가 충돌해 어느 직군도 확정하기 어려움.
- `CONTENT_UNAVAILABLE`: 정상 본문을 확보하지 못함. 수집 실패/빈 본문과 연계해 확인.
- `PENDING`: 저장되었지만 해당 규칙 버전으로 아직 분류하지 않음. 판별 실패와 구분.

화면은 다음 동작을 제안한다.

- 공고 목록에 **전체 · 직군 선택 · 미분류 N**을 항상 노출한다. 21개 분야는 개발, 데이터·AI, 플랫폼·인프라/시스템, 기획·비즈니스 등 묶음으로 찾되 여러 직군의 태그는 그대로 유지한다.
- 미분류 탭에서도 회사/사이트, 검색, 안 읽음, 최신 발견 순, 마감 포함 필터와 왼쪽 목록/오른쪽 캡처 흐름을 그대로 쓴다.
- 미분류 상세에는 사유와 판별에 사용한 저장 본문 버전을 보여준다. 여러 직군이 연결된 상세에서는 각 분야와 근거, 선택 배치형 여부를 확인할 수 있다.
- 미분류는 수집 분야가 아니므로 ‘미분류 수집’이나 가상의 회사별 지원 조합을 만들지 않는다. 수집 버튼은 전체/직군을 선택하는 기존 창을 연다.
- 직군 탭 건수는 복수 매핑으로 중복될 수 있다. 전체 수와 통계의 고유 공고 수는 공고 ID 기준으로 중복 제거하고, 분야별 합계가 전체와 다를 수 있음을 표시한다.
- 이전에 ‘확인 필요 보관함 대신 명확한 공고만 수집’하기로 한 원칙은 분야 수집의 포함 조건에 유지한다. 전체 수집으로 이미 저장된 공고의 세부 직군을 모른다고 삭제하지 않고, 요청한 미분류 탭에서 볼 수 있게 한다.

## 승인 후 구현 범위

1. 분류 결과를 수집 버튼 선택과 분리하고, 모든 저장 공고에 복수 직군 판별을 적용한다. 회사별 명칭/판별 전략은 유지한다.
2. **기존 440개는 저장 본문으로 일괄 재분류**한다. 외부 재수집·브라우저 렌더링·캡처·본문 버전 생성을 다시 하지 않는다. 최초 발견일·읽음·마감·과거 버전/캡처를 보존한다.
3. 변경된 자동 분류는 현재 직군 연결을 교체한다. 이전 자동 태그를 계속 더하기만 해 오분류가 남는 구조로 두지 않는다. 본문 버전/해시·분류 규칙 버전·판별 근거·시각을 남겨 규칙 변경 시 재분류할 수 있게 한다. `all`은 실제 직군 태그로 저장하지 않는다.
4. 이후 내용 변경 또는 분류 규칙 변경 때도 재판별한다. 내용이 동일해 캡처를 생략하는 수집에서도 분류 버전이 오래되었으면 저장 본문을 재사용해 판별한다.
5. 복수 매핑 표시와 미분류 탭을 구현하고, 현재 분야를 기준으로 목록/통계를 재집계한다. 과거 수집 실행의 선택 분야나 수집 결과/실패 기록을 바꾸지는 않는다. 당시 직군별 분류 상태를 복원하는 시계열 이력은 이번 범위에 넣지 않는다.
6. 공고별 검토표와 구현체 결과를 440개 전부 대조한다. 다르면 근거를 다시 확인해 규칙 또는 검토안을 수정하고 변경 이유를 남긴다. 데이터 무손실·동일 내용 재캡처 없음·미분류/복수 매핑 UI도 확인한다. 승인 전에는 분류기를 구현하거나 매핑을 바꾸지 않는다.
7. 실제 수집 지원 범위가 늘어나는 회사×분야 조합은 별도로 문서화하고 작은 조합부터 검증한다. 검토표에 분류할 수 있다는 이유로 새 수집기를 모두 검증 완료로 표시하지 않는다.

## 분석 자료 검증 범위

최신 본문 스냅샷의 공고 ID 440개와 검토표/JSON 440행이 일대일로 대응하는지, 누락·중복이 없는지 확인했다. 제안 직군 554개 연결과 단일/복수/미분류 집계가 일치하며, 기록한 근거 구절 510개가 해당 저장 본문에 실제로 존재함을 확인했다. 기존 분류된 11개의 연결은 제안안에도 모두 포함된다. 작업 종료 시 읽기 전용 DB 조회에서도 공고 440개·분류된 공고 11개·직군 연결 11개로 확인했다. 애플리케이션 변경이 없어 빌드·화면·실제 수집 버튼 검증은 수행하지 않았다.
