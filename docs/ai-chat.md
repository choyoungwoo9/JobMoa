# 전체 공고 AI 질문

JobMoa의 AI 질문은 공고 상세별 대화가 아니라 저장된 모든 공고를 대상으로 하는 전역 대화 기능이다. 회사·직군·열림/마감 조건은 질문에서 해석하며, 답변은 저장 공고 근거와 필요할 때의 외부 웹 근거를 함께 표시한다.

## 사용자 흐름

1. `AI에게 질문` 메뉴에서 새 대화를 만들거나 이전 대화를 연다.
2. 질문을 보내면 서버는 사용자 메시지, 대기 중인 답변 메시지, AI 작업을 저장하고 작업 ID를 바로 돌려준다.
3. 화면은 작업 ID로 SSE 연결을 열어 처리 상태, 웹 검색 중 표시, 답변 조각을 받는다.
4. 완료 후 공고 출처와 외부 웹 출처를 나눠 보여준다. 공고 출처는 저장 공고 상세로, 웹 출처는 새 탭으로 연다.
5. 화면을 닫거나 네트워크 연결이 끊겨도 작업은 취소하지 않는다. 다시 대화를 열면 DB에 저장된 답변과 마지막 이벤트 ID를 받아 이후 이벤트를 구독한다.

워커가 꺼져 있을 때도 질문은 저장된다. 화면에는 대기 안내를 표시하고, 워커가 시작되면 FIFO 순서로 작업한다. 같은 대화에서 아직 답변이 끝나지 않은 동안에는 추가 입력을 막는다. 최종 실패가 된 답변은 다시 시도할 수 있다. 대화를 삭제하면 해당 대화의 사용자/AI 메시지, 작업, 이벤트와 인용을 함께 삭제한다.

## 작업·스트림 계약

### 작업 생성

`POST /api/ai/conversations/{conversationId}/messages`

```json
{"content":"마감되지 않은 웹 백엔드 공고에서 쿠버네티스 경험을 요구하는 곳을 비교해줘"}
```

응답은 HTTP `202 Accepted`이며 `{ "taskId": "...", "messages": [...] }` 형태다. 작업과 메시지는 같은 DB 트랜잭션으로 저장된다. 요청 길이는 최대 6,000자다. 워커가 아직 없더라도 요청을 거절하지 않고 대기 작업으로 보관한다.

### SSE 이벤트

`GET /api/ai/tasks/{taskId}/events?after={eventId}`

각 이벤트는 MySQL `ai_task_event`에 저장된 증가 ID를 포함한다. `Last-Event-ID` 요청 헤더가 있으면 `after` 쿼리보다 우선한다.

| 이벤트 | 데이터 | 화면 동작 |
| --- | --- | --- |
| `status` | `{message, resetAnswer?}` | 자료 확인·답변 작성·워커 재대기 표시. 재시작 이벤트는 이전 시도의 부분 답변을 비운다. |
| `search` | `{message}` | `외부 웹 검색 중` 상태 표시 |
| `delta` | `{text}` | 답변 조각을 메시지에 추가 |
| `complete` | `{messageId, searchPerformed}` | 대화 메시지와 출처를 다시 불러오고 스트림 종료 |
| `failed` | `{message}` | 실패 메시지와 재시도 버튼 표시 |

이벤트 저장 트랜잭션이 커밋된 다음 현재 브라우저 구독자에게 보낸다. 연결을 다시 열면 전달되지 않은 저장 이벤트를 ID 순서대로 재생한다. 15초 간격 SSE keepalive와 프론트 NGINX의 프록시 버퍼 비활성화로 응답을 전달한다. 스트림 연결은 작업 자체의 생명주기를 제어하지 않는다.

### 재시도와 복구

작업자는 5분 임대 토큰을 받고 10초마다 갱신한다. 프로세스가 사라져 임대가 만료되면 서버는 15초 주기 복구에서 작업을 다시 `WAITING`으로 돌리고 메시지의 불완전한 답변을 비운다. 재시작 상태 이벤트를 남기며 이전 이벤트 기록은 유지한다. 같은 Codex 응답의 새 이벤트 ID부터 다시 스트리밍한다. 명시적으로 실패한 작업은 사용자가 재시도할 때 답변을 비우고 다시 대기열에 넣는다.

## 검색하는 공고와 인용

질문마다 모든 저장 공고의 회사·제목·위치·최초 발견·열림/마감·읽음·직군과 최신 저장 본문을 읽는다. 마감 공고도 포함한다. SQL 조회에는 열린 공고만 거르는 조건이 없다. `열린`, `지원 가능`, `마감`처럼 상태를 묻는 표현이 있으면 해당 상태만 검색 후보로 좁힌다.

전체 데이터의 회사·직군별 열린/마감/전체 건수를 모델에 함께 전달한다. 질문의 단어를 회사명·제목·직군·근무지·본문에 대조해 점수를 매기고, 관련도가 높은 최대 12개 공고의 본문 발췌를 전달한다. 본문은 공고당 최대 6,000자다. 질문에 관련된 본문이 많으면 뒤의 후보가 잘릴 수 있으며, 요약에는 후보 전체 수와 잘림 여부를 포함한다. 대화의 최근 질문/답변 일부는 후속 질문의 맥락으로 함께 전달한다.

작업 완료 시 모델이 요청한 공고 ID를 실제 작업 컨텍스트와 대조한 뒤 저장한다. 출처에는 작업 당시 회사·공고 제목·원문 URL·본문 버전 ID와 짧은 근거를 복사해 남기므로 이후 원본 데이터가 바뀌어도 답변의 인용 정보는 유지된다. 답변 텍스트에는 `[공고:id]`처럼 공고 근거 표시를 넣도록 지시한다.

## 외부 웹 검색

Codex CLI는 `web_search="live"` 설정으로 실행한다. 승인 정책은 CLI 실행 설정으로 `never`, 파일 시스템 샌드박스는 `read-only`로 고정하고 셸 도구를 끈다. 저장 공고만으로 답할 수 있는 질문은 검색하지 않고, 최신 정보·공고 밖의 회사 정보·일반 정보 등 저장 자료로 확정할 수 없는 질문은 검색하도록 지시한다. Codex가 검색 이벤트를 내보내면 백엔드는 이를 `search` SSE 이벤트로 즉시 보낸다.

외부 출처는 답변에서 `[웹:1]`처럼 표시하고 별도 인용 카드에 제목·URL·참고 이유를 보여준다. 저장할 때 URL은 HTTP(S) 공개 주소인지 검증한다. 검색 페이지의 전문은 저장하지 않는다. 웹 검색 여부와 출처 정보는 메시지·인용 테이블에 보관한다.

## Codex 워커 운영

Codex 워커는 필수가 아니며 Docker 안에서 실행하지 않는다. 기본 수집 서비스만 켜면 worker API는 연결 상태를 `false`로 보고한다.

필요 조건:

- macOS 로컬의 Java 21 이상
- Codex CLI 설치 및 `codex login` 완료
- Docker 백엔드가 `127.0.0.1:18080`에서 실행 중

명령:

```sh
./start.sh --ai-worker # 전체 Docker 앱과 워커를 시작
./ai-worker.sh status  # 워커 상태와 최근 로그 확인
./ai-worker.sh stop    # 워커만 종료
./stop.sh              # 워커와 전체 Docker 앱 종료
```

`CODEX_BIN`으로 Codex 실행 파일을 지정할 수 있고 `AI_WORKER_API_URL`로 worker API 주소를 바꿀 수 있다. 기본 모델 ID는 `gpt-6-luna`이며 변경 가능한 설정으로 노출하지 않는다. CLI는 사용자 프로필 설정을 읽지 않도록 실행하고, 셸 도구를 끄고 읽기 전용 샌드박스를 사용한다. 워커는 `backend/storage/ai-worker.log`에 로그를 남긴다.

## 경계와 개인정보

- AI 작업은 공고 상태 변경, 읽음 변경, 관심 표시, 수집 시작, 대화 삭제 등의 동작을 수행할 도구나 API를 받지 않는다.
- 작업 시점의 저장 공고 일부와 전체 건수 요약, 최근 대화 일부, 질문이 Codex CLI에 전달된다. CLI 인증이 연결된 Codex 서비스로 응답 요청이 나간다.
- 외부 웹 검색은 모델 응답 시 사용할 수 있다. 답변과 출처 제목·URL·이유만 저장하고 검색 페이지 콘텐츠는 따로 저장하지 않는다.
- 대화 삭제는 대화의 내부 메시지·작업·SSE 이벤트·인용 레코드를 지운다. 외부 서비스의 기록/보존 정책은 로컬 JobMoa에서 제어하지 않는다.
- 브라우저 연결 중단은 작업 취소가 아니다. 서버 종료 또는 워커 종료 후에는 임대가 만료되어 작업이 다시 대기하며, 워커가 재시작되면 새 응답 생성으로 이어간다.

## 구현과 검증 상태

이 문서는 2026-11-21 구현의 계약이다. 이번 변경에서 Flyway V11, Spring API/작업 큐/SSE, 선택형 Kotlin Codex 워커, 대화 화면을 추가했다. 백엔드는 `./gradlew compileKotlin`, 프론트는 Node.js 22.18에서 `npm run build`를 확인했다. Codex CLI의 실제 모델 응답·웹 검색·Docker에서의 SSE 연결은 사용자 로그인과 외부 응답을 사용하므로 이 구현 작업에서는 호출하지 않았다. 실제 앱 반영은 기능 브랜치 병합 후 별도로 진행한다.
