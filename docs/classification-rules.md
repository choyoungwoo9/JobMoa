# 신규 공고에 적용할 직군 판정 규칙 v0.5

**상태: 사용자 승인 후 제품 Kotlin 분류기에 적용(v0.5).** 사용자는 직군 확장 방향에 동의했고, 앞서 AI가 검토한 440개 분류안을 평가 정답으로 지정했다. 목적은 기존 공고에 태그를 수동 부착하는 것이 아니라, **새로운 공고에도 같은 규칙을 적용하는 분류기**를 만드는 것이다.

## 문서와 자료의 역할

| 자료 | 역할 |
| --- | --- |
| 이 문서 | 신규 입력에 적용할 판정 절차와 직군별 규칙 설명 |
| [규칙 명세 JSON](../backend/src/main/resources/classification/rules-v0.5.json) | 실제 평가에서 사용한 정규식·AND/OR/NOT·직군 의존 순서. v0.5의 정확한 조건 원본 |
| [고정 정답셋 manifest](analysis/classification-gold-v1.json) | 사용자가 지정한 gold-v1의 파일 SHA-256, 라벨 필드, 건수 고정 |
| [기존 440개 검토표](analysis/classification-440-2026-11-15.md) | 사례와 검토 설명. 정답 라벨은 대응 JSON의 `proposedCategories`로 고정 |
| [평가 결과](analysis/classification-evaluation-v0.5.md) | 일반 규칙 출력과 정답 비교. 완전 일치·누락·추가 오분류와 불일치 전부 |
| [오프라인 평가 도구](../scripts/analysis/evaluate-classification-rules.py) | 명세 JSON을 해석해 저장 본문만 평가하는 검토 도구. DB 연결·변경/수집 기능 없음 |

440개 정답 라벨을 규칙 안에 복사하지 않는다. 판정 함수 입력은 **공고 제목, 본문**이다. 공고 ID·URL·정답 라벨·기존 DB 카테고리·수집 버튼 선택값·공고 전체 제목에 대한 정답 룩업은 판정 입력으로 쓰지 않는다. ID는 **판정이 끝난 후** 정답과 결과를 연결할 때만 사용한다. `Backend Engineer`, `Product Owner` 같은 일반 직함/별칭 사전은 사용할 수 있다.

이번 명세는 회사명에도 의존하지 않는다. 회사별 목록 탐색·수집 후보 규칙은 기존처럼 별도다. 향후 회사별 본문 구간·직함 별칭 보정은 가능하지만 ‘이 회사의 이 URL은 백엔드’ 같은 예외는 금지한다. 새 회사×분야의 수집 지원은 이 문서만으로 구현/검증 완료가 되지 않는다.

## 입력과 출력

입력의 공식 세부 직군 메타데이터가 있으면 향후 보강 근거로 사용할 수 있다. 현재 저장 모델에 그 필드가 없어서 v0.5 평가는 제목·본문만 사용했다. 공식 분류가 없어도 본문에서 직무를 증명할 수 있어야 한다.

평가 출력은 직군 ID의 집합, 만족한 규칙의 짧은 본문 근거, 본문 구간 분리 방식이다. `all`은 실제 직군이 아니다. 제품 구현 시 규칙 버전·입력 본문 버전/해시·판별 시각·미분류 사유를 저장하는 방향은 [개선 제안](classification-proposal.md)을 따른다. v0.5 평가는 **직군 집합의 일치 여부**를 평가하며, 미분류 사유의 정확도나 화면 동작을 평가한 결과는 아니다.

## 1. 텍스트와 구간 정규화

1. Unicode NFKC, 줄바꿈, 앞쪽 불릿을 정규화한다. 정규식은 대소문자를 구분하지 않는다. 원본 본문을 바꾸지는 않는다.
2. `AI`, `ML`, `API`, `HAL`, `RAG` 등 짧은 영문 약어는 앞뒤 영문/숫자 경계를 확인한다. `HTML`의 `ML`, `maintain`의 `AI`, `storage`의 `RAG`, `challenge`의 `HAL`을 일치로 처리하지 않는다.
3. 본문을 **포지션 설명 / 담당 업무 / 필수 역량 / 우대 역량 / 채용·복지·관련 콘텐츠**로 나눈다. 명세 JSON의 `parser`가 실제 구간 시작/종료 표현이다.
4. 담당 업무는 행/불릿 단위로 나눈다. 하나의 업무 단위 안에서 대상과 행위 조건을 함께 확인한다. 다른 행의 ‘API’와 ‘디자이너’를 임의로 연결해 직군을 만들지 않는다. 여러 문장이 한 불릿에 있으면 v0.5에서는 같은 업무 단위다.
5. 담당 업무 제목이 있으면 그 구간을 우선한다. 없으면 포지션 설명을, 그조차 없으면 필수/우대/채용 구간 앞의 내용을 보조 구간으로 쓴다. 결과에 `structured`, `position-fallback`, `unstructured-fallback`을 기록한다. **fallback이 회사 소개와 업무 설명을 완벽히 분리한다는 보장은 없으며 오분류 평가 대상이다.**
6. 한국어 예: 주요업무, 담당할 업무, 업무내용, 다음 업무를 통해 목표를 달성해요, 합류하면 함께할 업무, 진행할 프로젝트. 영어 예: Responsibilities, What You'll Do, Role Overview. 일본어 예: 主な業務内容, ポジション概要. 중국어 예: 工作內容, 職務內容. 실제 전체 표현은 JSON에 둔다.
7. `우대사항`, `이런 경험을 우대합니다`, `Preferred Qualifications`, `あると望ましい` 뒤 내용은 담당 업무로 쓰지 않는다. 필수 역량은 보조 판정에서만 쓰며, 우대 기술만으로 직군을 추가하지 않는다. 이미 실제 클라이언트/어드민 UI 개발이 명시된 경우 React 등은 웹 영역인지 해석하는 보강 근거로만 사용할 수 있다.
8. 채용 절차·지원서·면접·복지·관련 공고·회사 소개·‘회사 전체가 무엇을 한다’는 문장을 실제 담당 업무의 직접 근거로 취급하지 않는다. v0.5는 구간·표현 필터로 이를 근사하므로 미등록 표현은 남은 오분류 원인이 될 수 있다.

## 2. 판정에 사용하는 조건

| 조건 | 의미 | 예 |
| --- | --- | --- |
| 직무 정체성 | 일반 직함·회사별 별칭으로 특정 역할이 명시됨 | Server Developer, 프론트엔트/프론트엔드, Product Owner |
| 업무 대상 | 지원자가 직접 다룰 시스템/산출물 | 서버 API, 웹 UI, 학습 모델, 데이터 마트, DB 백업 |
| 수행 행위 | 대상에 실제 수행하는 작업 | 설계·구현·개발·구축·운영·학습·판매·계약 |
| 소유 범위 | 본인이 담당하는 산출물인지, 공통 플랫폼인지 | 전사 배포 플랫폼 개발 vs 자기 서비스 배포 |
| 필수 역량 | 이미 존재하는 업무를 해석하는 보강 근거 | 결제 서비스 개발 + 필수 Spring 경험 |
| 배제 문맥 | 다른 사람의 업무, 도구 사용, 부가 가능성, 우대사항 | 백엔드 개발자와 협업, AI 코딩 도구 사용, 필요하면 참여 |
| 선택 배치 | 한 모집 안에 여러 확정된 배치 경로가 있음 | frontend or backend, iOS 또는 Android SDK |

직무 정체성만으로 합격시키지 않는다. 구현 방식은 두 경로다.

- **직접 경로:** 담당 업무의 같은 단위에서 해당 직군의 구체적 대상과 수행 행위가 함께 확인되고, 배제 문맥이 없다.
- **보강 경로:** 직함이 특정 역할을 가리키고, 그에 맞는 실제 업무가 있으며, 필요한 경우 필수 역량이 그 해석을 보강한다. 제목이 Backend여도 실제 주업무가 테스트/DB/인프라뿐이면 이 경로를 차단한다.

예를 들어 `Software Engineer`라는 제목이라도 담당 업무가 ‘Spring 기반 결제 서비스를 개발’이면 백엔드 직접 경로가 성립한다. 반면 제목이 `Back-end Engineer`라도 실제 업무가 ‘API 테스트 자동화 프레임워크 개발’이면 QA 경로가 성립하며 백엔드로 자동 통과하지 않는다.

현재 v0.5는 문장 주어·목적어를 완전한 언어 모델로 해석하지 않는다. 위 조건을 구간·동일 행의 대상/행위 패턴·협업/선호/조건부 표현의 배제로 근사한다. **상세 의미를 완벽하게 판정하는 규칙으로 주장하지 않고, 정답셋과의 차이를 계측한다.**

## 3. 직군별 일반 규칙

각 행은 제목과 무관하게 새로운 공고에도 적용할 판단 계약이다. 실제 표현 사전과 세부 AND/OR/NOT 조건은 [명세 JSON](../backend/src/main/resources/classification/rules-v0.5.json)의 동일 ID를 따른다.

| ID / 직군 | 직접 경로의 대상·행위 | 보강 경로 | 제외·경계 |
| --- | --- | --- | --- |
| `web-backend` / 웹 백엔드 | 서버/백엔드/API/게이트웨이/마이크로서비스의 설계·개발·구현. Spring/Django/Nest 기반 서비스 구현 | 서버/백엔드/Node.js/풀스택 등의 정체성 + 실제 서비스/도메인 업무 + 필수 서버 역량. 일반 Software Engineer는 다른 세부 정체성이 없을 때만 보강 | 다른 백엔드 개발자와 협업, API 소비/테스트, 프론트엔드 서버/SSR, 인프라 권고, 순수 데이터/ML 플랫폼을 서버로 확대하지 않음 |

| `fullstack` / 풀스택 | 백엔드·프론트엔드가 각각 통과하고 같은 포지션에서 양쪽을 구현한다는 접속 관계가 확인됨 | 풀스택 직함도 양쪽 분야의 업무 근거가 필요 | ‘프론트 또는 백엔드’ 선택 배치, 다른 팀과 협업, 팀 전체의 풀스택 역량은 제외 |
| `data-engineer` / 데이터 엔지니어 | 데이터 수집·입수·적재·ETL/ELT·CDC·DWH/마트·배치/스트리밍/분산 처리 기반의 개발·운영 | Data/Analytics Engineer 정체성 + 실제 데이터 모델·워크플로/데이터 제공 업무 | 단순 SQL 분석, 학습 데이터 준비만 수행, 인프라 로그 수집, 데이터 거버넌스 정책만 기획하는 역할과 구분 |

## 4. 복수 매핑과 충돌 처리

1. 21개 직군을 독립적으로 평가한다. 단일 주직군 선택, 분야 간 무조건 상호 배제는 하지 않는다.
2. 여러 분야가 통과하면 모두 연결한다. 풀스택은 **백엔드와 프론트엔드가 둘 다 통과**하고 동일 담당 근거가 있어야 한다. 통과하면 세 분야에서 조회된다.
3. 명시적인 선택 배치는 해당 경로 모두에서 조회하되 풀스택으로 보지 않는다. ‘경험/역량에 따라 frontend 또는 backend’는 확정된 모집 경로이고 ‘향후 다른 OS도 맡을 가능성’은 현재 직무가 아니다.
4. 제목과 실제 업무가 충돌하면 업무 대상을 우선한다. 업무 자체가 모순되면 확실한 분야만 연결하고 추가 분야를 보류한다. 이 판단의 구체적인 표현/충돌 조건도 명세에 있어야 하며 ID별 예외로 해결하지 않는다.
5. 업무상 근거가 없는 추가 태그는 오분류다. 정답에 없는 태그 하나가 늘어도 그 공고는 완전 일치에 실패한다.
6. 통과한 분야가 없으면 미분류다. 미지원 역할, 근거 부족, 내용 미확보, 분류 대기 등 제품상 사유 구분은 별도 저장한다.

v0.5는 일부 직군 판정에 앞서 통과한 전문 직군을 참고한다. 예를 들어 QA/인프라로 실제 업무가 확인되면 일반 백엔드 직함을 통한 보강 경로를 차단하고, 풀스택은 마지막에 판정한다. 실제 순서는 JSON의 `ruleEvaluationOrder`다. 이를 바꾸면 결과가 달라질 수 있으므로 규칙 버전 변경으로 취급한다. `taggedAny`는 명시한 직군 중 하나 이상을 뜻하며, 두 분야를 모두 요구할 때는 별도의 AND 조건을 사용한다.

## 5. 정답과 평가 계약

- **gold-v1:** 기존 JSON의 `proposedCategories` 집합을 정답으로 고정했다. 미분류는 빈 집합이다. 설명·보류 후보·수집 버튼으로 정답을 덮어쓰지 않는다. SHA-256이 바뀌면 평가 도구가 거부한다.
- **정확 비교:** 440개 모두의 예측 집합과 정답 집합이 같은지 비교한다. 공고 완전 일치율과 직군별 TP/FP/FN·정밀도·재현율·F1을 함께 기록한다.
- **변경 정책:** 규칙을 바꿀 때 같은 정답셋 전체를 다시 평가한다. 점수만 맞추려고 URL/ID/고유 전체 제목 예외를 추가하거나 불리한 공고를 제외하지 않는다.
- **정답 오류 의심:** 라벨과 검토 설명이 모순되거나 본문 근거가 누락됐어도 gold-v1은 유지한다. 별도 검토 후보로 공개하고 사용자가 수정하면 gold-v2를 만든다. 새 버전의 점수와 이전 버전 점수를 혼합하지 않는다.
- **일반화:** 같은 440개를 보며 만든 규칙을 같은 440개에 적용한 결과는 개발/회귀 평가다. 신규 사이트·미사용 공고의 정확도를 증명한 결과가 아니다. 실제 신규 공고로 별도 정답셋을 만든 뒤 추가 평가할 수 있다.

## 6. 현재 평가와 남은 작업

v0.5는 고정 정답과 **378/440개 완전 일치(85.91%)**했다. 태그 기준 정밀도 91.85%, 재현율 95.67%, micro F1 93.72%다. 추가 오분류 47개 태그, 누락 24개 태그가 있으며 서로 겹칠 수 있다. 불일치 공고 62개를 모두 [평가 문서](analysis/classification-evaluation-v0.5.md)에 공개했다.

따라서 이전 검토안에서 ‘439개를 분류 가능’하다는 수치는 정답셋의 분류 상태이며 **현재 규칙이 439개를 올바르게 분류했다는 뜻이 아니다.** 현재 규칙의 완전 일치 결과는 378개다. 제품에 적용하기 전 일반 규칙의 누락/오분류와 정답 검토 후보를 다뤄야 한다.

제품 분류기는 `classification` 영역의 `PostingClassifier` 계약과 `RulePostingClassifier` 구현이다. 규칙 JSON은 백엔드 리소스 한 곳에만 보관하며 Docker 이미지에 포함한다. v0.5 승격은 버전·상태 메타데이터 변경이며 v0.5-draft의 판정 조건은 유지했다. Kotlin 결과를 기존 440개 스냅샷의 Python 출력과 대조해 직군 집합과 본문 구역 추출 모드가 모두 같은지 확인한다. 정답셋은 수정하지 않는다.

저장 완료 시 `all`을 포함한 모든 수집에서 전체 직군을 판정한다. 변경 없는 공고는 기존 본문을 재사용한다. 자동 태그는 새 결과로 교체하며, 규칙 버전·입력 제목/본문 SHA-256·판별 문장·판정 시각·미분류 이유를 `posting.classification_json`에 저장한다. 입력 해시는 원문 제목 + 줄바꿈 + 저장 본문이며 본문 버전은 추가하지 않는다. `POST /api/classifications/rebuild`는 저장된 최신 본문만 재분류하고, 공고별 잠금/트랜잭션으로 읽음·마감·최초 발견일·버전을 보존한다. 실패한 공고 ID는 응답으로 반환하고 다른 공고는 계속 처리한다.

목록의 ‘미분류’는 직군 연결이 없는 공고이며 수집 분야가 아니다. 새 8직군은 자동 분류와 조회를 지원한다. 회사별 분야 수집은 기존 지원 조합과 후보 탐색 범위를 유지하며, 새로운 회사×직군 수집을 검증한 것으로 안내하지 않는다. 분야 수집의 최종 본문 판정은 제품 분류기와 동일하다.

실제 제품 검증과 초기화 결과는 [구현 검증 기록](analysis/classification-implementation-v0.5.md)을 참고한다.
